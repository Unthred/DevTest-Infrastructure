# Docker foundation (issue #2)

This module is the trusted host-side container boundary for future `dev-test` commands. It does not expose a new end-user launcher. Build and browser commands will enter through the single `dev-test` CLI in issue #8. The [runner example](../docker/runner.example.json) shows the trusted configuration shape; [Compose](../docker/compose.example.yaml) documents equivalent hardening without becoming a separate run path.

## Image and storage policy

[`images.lock.json`](../docker/images.lock.json) records official MCR image tags, immutable RepoDigests and the 2026-10-30 Tower inspection date. This is a local observation, not a claim that the tags are current upstream. The runner accepts only these exact repositories and 64-character lowercase SHA-256 digests. It uses `--pull=never`; a missing digest is a reported environment precondition, never an implicit download or tag fallback. Image updates belong to issue #12.

The trusted host caller provides an exact allowlist of real project roots under `/mnt/user/projects`, a storage root under `/mnt/cache`, a non-root UID/GID and bounded CPU, memory, PID, shared-memory and wall-time limits. The source tree mounts read-only at `/src`. `/work` and `/out` share one fixed-size ext4 loop image; the cache has its own fixed-size image. Build/test mount the cache read-only, and only an explicit `restore` phase mounts it writable. The caller must select a command preset or otherwise validate arguments so no secret value is put in a command line; the runner rejects control characters and never passes the host environment into the container. Network access is `none` in this foundation. A networked restore phase needs a separately reviewed policy.

Each run uses a unique name and run-id label, drops every Linux capability, denies privilege gain, makes the root filesystem read-only and uses an explicit tmpfs. The host runner starts Docker without a shell. On success, subject failure, timeout or interruption it verifies container ownership by label and removes only its own leftover container. An unverifiable Docker daemon or foreign name collision reports incomplete cleanup; it never removes another container. Run volumes remain mounted for the caller to inspect; `releaseRunVolume` verifies the backing file before unmounting. The cache mount remains for reuse. The smoke uses a unique temporary storage root and removes its own images and mounts after verification.
Before starting, the runner refuses any pre-existing container with the generated name, even if it carries the same run label. A reused run id cannot take over a container from a previous attempt.

The Docker CLI subprocess gets only `PATH`, `HOME` and, for a rootless daemon, an owner-only `XDG_RUNTIME_DIR` with its matching Unix `DOCKER_HOST` socket. TCP Docker endpoints and other host environment values are refused or omitted. The container receives no host environment values.

## Validation

Run `node tools/validate-project.mjs` and `node --test 'tests/**/*.test.mjs'`. The Docker tests cover malformed digests, foreign images, exact allowlists, unsafe paths/IDs/limits/network/argv, hardening flags, foreign-container refusal, success, subject failure, timeout and incomplete cleanup. On Tower, `ionice -c 3 nice -n 19 node tests/docker-smoke.mjs` runs positive, failing-subject and hard disk limit probes through the local pinned .NET SDK image with no network, then verifies no container remains. The disk probe attempts a 96 MiB write into a 64 MiB filesystem and requires the write to fail with a distinct subject exit code before the container exits. It touches only generated cache-pool run workspaces and does not alter a production service. Keep the command result and image digest on issue #2; do not treat a simulated unit test as a real Docker smoke.

## Limits

The runner has no OpenBao access because this foundation does not need credentials. Issue #7 designs scoped secret delivery. Issue #8 wires the single CLI and result contract. A host reboot, production application mutation, or new image pull is outside this smoke.

## Review corrections (Claude, PR #19 review)
- **Disk budget (`diskMb`, `cacheMb`).** The trusted host creates fixed-size, sparse, no-COW ext4 loop images under its storage root. `/work` and `/out` share the `diskMb` image, so an over-limit aggregate write fails with `ENOSPC` inside the container. The cache has a separate `cacheMb` image and is writable only in the explicit `restore` phase. If image creation or mounting fails, the runner refuses to start the container. The 200 ms scanner and per-file `fsize` ulimit are secondary checks, not the disk ceiling. No pool-wide btrfs quota is enabled. Loop images use cache-pool disk; they do not reserve RAM like tmpfs. The small `/tmp` tmpfs is 64 MiB per container, plus configured shared memory.
- **Exit mapping.** The container is not started with `--rm`; its exit code and OOM flag are read before removal. Subject outcomes (127, 126, 137, OOM) are exit 1 with a `reason`; only a Docker failure with no container state is exit 6.
- **Logs.** Docker uses `--log-driver=none`. The host consumes stdout/stderr through pipes, caps its byte counters at 1 MiB per stream and discards the bytes without persisting them. There is no raw subject log to scan or retain. Future evidence export must add a fail-closed secret scan under issue #7; the retained run image is private and must not be published as an artifact before that gate exists.
- **Swap and init.** `--memory-swap` equals `--memory` and `--init` is set. On this Tower the kernel reports "does not support swap limit capabilities", so the swap flag is requested but **not enforced here**.
- **Project mount.** The whole project directory is readable by the subject, including untracked files such as `.env`. `--network=none` limits exfiltration to what is written under `/out`. Prefer a tracked-files export for projects holding local secrets.
- **Left-over containers.** Without `--rm`, a runner killed with SIGKILL leaves a stopped container labelled `devtest.run-id`; a sweeper belongs with issue #8.
