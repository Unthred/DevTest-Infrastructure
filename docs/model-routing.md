# Model routing per job type (issue #64)

`supervisor/team.json` carries a `models` table: `allowance_threshold` (default 0.8) and, per agent, a `{model, effort}` for each job type (`implement`, `continue`, `fix`, `review`, `rebase`, `ci-fix`) plus an optional `strong` entry used on escalation (default: the agent's `implement` entry) and an optional `low` entry used for fix-round re-reviews while the reviewer's allowance is low (issue #56). `team.local.json` may override any entry or the threshold (`models` key; merged per entry, validated structurally).

- **Aliases only.** Claude uses `opus` / `sonnet` / `haiku` / `fable`; Codex omits `model` (its standard model) and varies reasoning effort; a Codex model name must be one of the models listed in the Codex manifest (the CLI has no way to validate a name offline) or it is dropped with a warning. No version strings.
- **What a CLI accepts** is declared by its manifest (`supervisor/providers/*.json` → `models`: `aliases`, `pattern` for full names, `efforts`, `model_args`, `effort_args`). Core and the team loop name no provider (D-012).
- **Fallback.** A model or effort the manifest does not accept is dropped: the CLI default is used, the job still runs, and a warning is stored on the job (`modelWarning`), shown in the tick report (`warnings`). The adapter re-checks the values before building argv, so nothing unvalidated reaches the command line.
- **Escalation** (non-implement jobs): the next attempt uses `strong` when an earlier job of the same work ended `incomplete` on a cheaper model, or when the PR has drawn CHANGES twice (repair jobs: fix, ci-fix, rebase, continue). The reason is stored in `modelReason`.
- **Allowance-aware.** When the provider-reported weekly utilisation (freshest job allowance record, window not yet reset) is at or above the threshold, every job type except `implement` and `continue` keeps its cheap entry, and escalation is suppressed. Scheduling by allowance (modes, reassignment, cost fit) is described in [allowance-scheduling.md](allowance-scheduling.md); while an agent is not in `normal` mode, escalation is suppressed and a fix-round re-review uses its `low` entry when one is configured.
- **Visibility.** Each job records `model`, `effort`, `modelSource` (`configured` / `escalated` / `allowance`), `modelReason`; `ai-agent --supervisor status` prints them; the dashboard jobs tables have Model and Effort columns and the Usage page has "Tokens per job type and model".
