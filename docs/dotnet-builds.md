# .NET SDK command planning (issue #3)

The `dotnet/commands.mjs` module prepares argv arrays and `dotnet/run.mjs` passes them to the existing trusted Docker runner; neither exposes a second CLI. Select SDK `8`, `9`, or `10`, choose `restore`, `build`, or `test`, then resolve a single solution/project in the selected working directory. Ambiguous discovery fails with a request for an explicit project. Host paths are translated to `/src/...`; project and working-directory symlink escapes are rejected.

`runDotnet` selects the corresponding exact image key (`dotnet-8`, `dotnet-9`, or `dotnet-10`) from `docker/images.lock.json`, then delegates the plan to `runContainer`. Each SDK uses its own bounded NuGet cache (`nuget-sdk-8`, `nuget-sdk-9`, or `nuget-sdk-10`). Restore receives the writable cache mount and an explicit `/cache/<sdk>` package path. It can populate packages from an explicit local source or reuse packages already cached; all containers remain network-disabled, so remote package restore is not supported. Build and test set `RestorePackagesPath` to the same cache, use the runner-created empty source, and retain the cache read-only. SDK artifacts and intermediate files go under `/work/artifacts`, never into the read-only `/src` mount.

On Tower, `ionice -c 3 nice -n 19 node tests/dotnet-smoke.mjs` creates a throwaway package feed and project under a unique `/mnt/user/projects` directory. For each pinned SDK it restores from that feed, restores again with an empty source to prove package-cache reuse, and performs a real build with the cache read-only. The smoke uses a unique cache-pool storage root and removes only those generated paths. It does not pull images, change services, or reboot Tower. This is a build/cache smoke, not a test-project/TRX or coverage acceptance test; those belong to #4.
