# Opt-in unattended supervisor (issue #15)

**Implementation state:** first version on `codex/issue-15-supervisor`; installation and independent review are tracked separately in `docs/ai/CURRENT_HANDOVER.md`.

## Contract

`ai-agent` remains role-first and interactive by default. The optional `ai-agent --supervisor ...` path forwards to `ai-supervisor`; no existing tmux session is inspected or modified. Each job specifies a registered provider, repository, dedicated feature worktree, issue number, approved scope, allowed actions, task prompt and optional handover path. The repository and worktree must be distinct roots of the same Git repository. Jobs for different issues can run in parallel in different worktrees. A worktree or issue is exclusively leased until the terminal job is explicitly released.

The registry `supervisor/providers.json` is schema version 1 and points to versioned provider manifests and adapter modules. The manifests follow Claude’s issue #1 provider contract: unknown fields and missing capabilities are rejected, capability values are `supported`, `unsupported` or `unverified`, and `billing.fallback_to_other_billing` must be `false`. Claude and Codex launch and checkpoint successfully, but real limit detection, reset parsing and session resume remain **unverified**. `autoResume: true` is rejected for these production manifests until redacted real output and resume evidence are captured. A future provider can register an adapter and manifest without changing the core. Provider commands are never read from issue or handover content.

Job state and event summaries are stored under `/mnt/cache/ai-supervisor` (mode 0700; job files 0600) with atomic rename/fsync. Raw provider output is processed in memory and discarded. Checkpoints record Git HEAD, up to 80 tracked status lines, a hash of the first 64 KiB of an optional handover, and up to four allowlisted heading labels. Handover body text is not copied. If Git changes while the handover does not, the job is marked stale and a later resume blocks until the handover is updated. The worker checkpoints every 60 seconds and on exit. Each process has an exact PID/start-time claim; stale workers and leases require explicit recovery. `reconcile` can restart an eligible paused job after reset, while a running orphan becomes blocked for inspection. Run `daemon` under an approved persistent host manager to reconcile every minute after a host restart.

For a provider whose capabilities have been verified as supported, a provider-reported verified reset waits until at least two minutes after reset, with a minimum five-minute delay. Long waits are divided into day-sized sleeps and never wake early. An unverified or absent reset gets conservative 1, 2 and 4 hour waits, then blocks. Transient rate limits get bounded minute-scale retries. Context exhaustion starts a fresh session from issue, Git and handover state; network errors and crashes get bounded retries. Authentication failures, approval requests and spend/budget limits block for a human. The worker makes no provider call during a wait. It records a unique attempt ID before each launch. A session ID is reused only when that provider’s resume capability is verified as supported; otherwise the adapter starts fresh with the original approval scope.

Claude and Codex launch only when their local CLI reports subscription login. API-key environment variables are removed from child environments. This avoids silent API-key fallback; it does not guarantee the provider will never change its CLI behavior. Authentication material stays in the existing CLI secure storage. No OpenBao secret is needed for these subscription sessions; future credentials should use a scoped OpenBao identity and must not be added to job specs, logs or the registry.

## Job spec and commands

Create a private JSON file outside Git:

```json
{
  "role": "devtest",
  "provider": "codex",
  "repository": "/mnt/user/projects/DevTest-Infrastructure",
  "worktree": "/mnt/user/projects/DevTest-Infrastructure-codex-15",
  "issue": 15,
  "scope": "Implement issue #15 on the feature branch",
  "allowed_actions": ["edit", "test", "push_feature_branch"],
  "prompt": "Continue the approved issue. Preserve the handover and stop at review/merge gates.",
  "handover": "docs/ai/CURRENT_HANDOVER.md",
  "autoResume": false
}
```

The `allowed_actions` values are a closed list: `read`, `edit`, `test`, `push_feature_branch`, `create_pr`, `update_issue`, `update_handover`. Run `ai-agent --supervisor dry-run --spec FILE`, then `ai-agent --supervisor start --spec FILE`. Use `status [ID]`, `logs ID`, `pause ID`, `stop ID`, `resume ID`, `auto-resume ID --no-auto-resume`, `reconcile` and `release ID`. `start --foreground` is for supervised testing. `release` only accepts terminal jobs. Jobs recorded before child start times were captured have no `childStart`; for those the liveness check falls back to process existence minus zombies, so a reused PID can keep the job's leases (it fails closed). For such a legacy job, run `release ID` manually once it is terminal. Never put credentials in the spec. The spec is operator supplied; its scope remains subject to project and role policy.

`allowed_actions` constrains the supervisor's prompt and spec validation; it does not technically sandbox provider tool calls. Claude runs with its configured `--permission-mode auto` and Codex uses its configured profile. The provider's own approval, sandbox and execution controls remain authoritative. Review the selected role and profile before starting unattended work.

## Validation and limits

Run `node --test tests/supervisor.test.mjs` and `node tests/real-smoke.mjs WORKTREE`. The latter performs one read-only prompt per installed subscription CLI and summarizes results without exposing provider output. Fake-clock tests cover verified and unverified resets, long waits, transient rate limit, auth, context, approval, network, crash, duplicate job, stale-worker and handover cases. Manifest negatives cover unknown fields, missing capabilities and billing fallback.

Provider usage-limit text and reset formats are based on narrow simulated fixtures; real subscription-limit output has not yet been observed. A provider response that changes format will block or fail safely rather than claim a valid reset. The daemon needs an approved host startup mechanism for reboot recovery. The process is not an independent acceptance authority and cannot grant permission for deployment, purchases or merges.

## Rollback

Stop or pause only supervisor-owned jobs, remove the optional `--supervisor` forwarding block from the backed-up `ai-agent` launcher, and remove the versioned supervisor wrapper/install. Preserve the private state directory and handover for recovery. Existing interactive tmux sessions do not require changes.

## Tower installation

After reviewing the branch and confirming no other launcher edit is in progress, run `bash tools/install-supervisor.sh`. It runs the fake test suite, copies the committed supervisor to the private `/mnt/cache/ai-supervisor/versions/<commit>` tree, backs up `/root/bin/ai-agent`, adds only an explicit `--supervisor` forwarding case, and installs `/root/bin/ai-supervisor`. Verify `bash -n /root/bin/ai-agent`, `/root/bin/ai-agent-tests`, and `ai-agent --supervisor help`. This opt-in path does not start a daemon or touch existing tmux sessions. Roll back the launcher with `bash tools/rollback-supervisor.sh COMMIT` after pausing supervisor-owned jobs; retain state for recovery.

For a reviewed follow-up commit after installation, run `bash tools/upgrade-supervisor.sh`. It keeps the original launcher and existing job state, copies the new committed version, backs up the prior wrapper and switches only the wrapper path. Active workers continue on their originally loaded version; pause them first if adapter behavior must be consistent across a switch.

## Reconciliation after Tower restarts

The installed version is also exposed through the private `/mnt/cache/ai-supervisor/current` symlink, which points to a committed version under `versions/`. Tower's User Scripts plugin can run `tools/install-reconcile-user-script.sh` to add one five-minute custom schedule. Its script calls `node /mnt/cache/ai-supervisor/current/supervisor/cli.mjs reconcile`; it neither invokes a provider nor spends tokens unless a job is due and its verified capabilities permit auto-resume. The installer backs up the existing plugin schedule and cron files in the private cache state tree, preserves all existing schedule entries, calls Unraid's supported `update_cron`, and verifies the active `/etc/cron.d` crontab. `tools/remove-reconcile-user-script.sh` removes only this entry and script. Both scripts have a temporary-root test mode used by CI.

The schedule is stored on `/boot` and active on this Tower. A host reboot has **not** been performed, so actual post-reboot persistence and provider continuation are unverified. If `/mnt/cache` or Node is unavailable at a tick, the script exits; the next tick can reconcile after those dependencies return. A stale worker or child claim blocks takeover until a human inspects it. Existing interactive sessions and production Home Assistant are outside the reconciliation scope.

## Cron environment (issue #35)
Cron runs the reconcile script with almost no `PATH`, so `gh`, `codex` and `claude` were not found and scheduled ticks failed with no trace. `tools/install-reconcile-user-script.sh` now pins an explicit `PATH` (the directories of the `command -v` results for `node`, `gh`, `git`, `codex`, `claude`, `flock`, plus the system directories) and `HOME` in the generated script, runs one reconcile at a time under `flock` (an overlapping run skips), and appends one line per tick (`<time> rc=<n> <output tail>`) to `/mnt/cache/ai-supervisor/reconcile.log`, trimmed only above 1 MiB while the lock is held. The installer refuses if `gh`, `git` or `flock` cannot be found. A failed team tick, or one that skipped an item, makes a scheduled `reconcile` exit 1 and log a non-zero `rc`; a missing CLI or `node` logs `rc=127` with the reason. The enable gate (issue #40) is `tools/verify-reconcile-env.sh`, run by the installer before anything is written: under `env -i` with the pinned `PATH`/`HOME`, from `/` rather than the caller's directory, it runs `ai-supervisor preflight` (repo root, `gh` access, `origin/main` register read and D-020 approval, and both providers' preflights against the configured product repository; exit 3 with named failing checks) and `team tick --dry-run` (the live tick's own planning path; a dry run now also requires the register and D-020, like a live tick). The dry run counts only when it exits 0 and its stdout (not stderr) is JSON with an `actions` array and no string `skipped`, the same strict check as the self-upgrade health check; a busy tick lock is named in the failure so it is retried, not debugged. **Limit:** a dry run never reaches `reconcileOnce`, `selfUpgradeBefore/After` or the pending config migrations, which only a live tick runs, so a failure specific to those under the cron environment is not caught by the gate; the first live ticks (and their `rc` in the log) are the check for them. The installer exits 2 and installs no schedule unless both pass and the dry run returned a plan. Because a dry run now always needs the `origin/main` register, the self-upgrade health check (`team tick --dry-run`) fails if the register cannot be read right after an upgrade; it is retried three times with backoff (15 s, 30 s) before that can trigger a rollback. A missing provider binary is reported as `preflight_failed` (a blocked job), never as `auth_error`; a missing `gh` is a named error; transient GitHub transport errors are retried three times with backoff inside the tick. Not yet implemented: the dashboard indicators ("last tick failed", "no successful tick in 10 minutes", consecutive failures, stale leases) belong to issue #32.

## `team status` (issue #39)

`ai-supervisor team status [--json] [--no-github]` (installed as `team-status`) prints a short plain-English summary: what each agent is doing, what happens next (the dispatcher plan, or a plain reason nothing will start), problems, pull requests with CI and the latest verdict, merged today, and the tick schedule. It is built on `buildView` from the dashboard (#32), so the two share one set of rules. It is read-only and makes no model call. It reads the tick's cached GitHub data (`dashboard/cache.json`, which now also holds recently merged PRs); only when that is older than 10 minutes does it make one `gh` call per section (open PRs, issues, merged PRs), falling back to the cached copy with a note on failure. Output is redacted. `install-supervisor.sh` and `upgrade-supervisor.sh` write `/root/bin/team-status`, a wrapper around `ai-supervisor team status`, so it follows every later upgrade. Not part of this change: `team alert` (event-driven Slack alerts, issue comments), which needs the OpenBao-delivered webhook and is a separate piece of work.

## Continue jobs, idle reasons and fix-limit alerts (issue #50)

- **Continue.** When an agent has its own DRAFT pull request (branch `<prefix>issue-<n>-…`) for an issue it owns that is open, not delivered, not labelled `needs-homeowner` and has all prerequisites closed, the dispatcher plans a `continue` job on that branch instead of skipping it. It sits between review and implement in the agent's priority, is bounded per PR by `max_fix_attempts` (`continueAttempts` in the team state) and its post-condition is a new pushed head or a PR that is no longer a draft. The job never merges.
- **Idle reasons.** Each idle agent on the dashboard and in `team status` states why in plain words: `waiting for homeowner: fix limit reached on #41`, `only work is draft #28`, `all issues blocked by #3`, `waiting for review of #29`, and so on, with links on the dashboard.
- **Fix-limit alerts.** When the per-PR fix limit is reached, the one `needs-homeowner` notice is followed immediately by an alert through the same channel as the self-upgrade alerts (`alerts.command` in `team.local.json`, text on stdin, logged to `team/alerts.jsonl`), carrying the PR link and the decision needed. Without `alerts.command` the Unraid notify script is used; with neither, delivery fails (logged as `delivered:false`). An alert is retried on later ticks until the channel accepts it, then never repeated, and a failure never undoes the notice.

## Drain before a self-upgrade (issue #136)

The tick checks for an installable commit before the team step, every tick. When main is ahead of the installed commit and the range is eligible, the tick enters **drain**: it starts no new job, lets running jobs finish, installs at the first moment none is running, then resumes dispatch (also after an install failure or rollback). Drain is bounded by `self_upgrade.drain_max_minutes` (default 30, 1-720; overridable in `team.local.json`). When the bound is reached the install goes ahead; it replaces files only and never stops a running job. The wait belongs to one target: when main moves to a newer commit during the wait, the bound starts again for that commit. An environmental pre-check failure is retried with backoff (see below); each retry with jobs running holds dispatch again for up to the drain bound (a latched failed pre-check itself never holds). `team status` and the dashboard show "install pending since HH:MM (upgrade to <sha>), draining (N jobs running)".

**Installs are batched (issue #695).** Merged is not installed: a merge makes main newer, but the install begins draining only when `self_upgrade.min_install_gap_minutes` (default 45, integer 0 to 1440, 0 turns batching off) have passed since the last install finished (verified, or rolled back). Inside that window, with jobs running or work planned by the previous tick, the step returns `batched`: no hold applies, new jobs start normally, and merged work waits. Nothing running and nothing planned installs at once, since it costs no work. The window is kept in `self-upgrade.json` (`lastFinishedAt`), so a restart keeps it. Two urgent cases skip the window and still drain as before: the previous install rolled back (after the latch is cleared), and `ai-supervisor self-upgrade install-now` (the homeowner asks; the hand-install route also bypasses it). Urgency is spent only by an install: `install-now` is refused when the installed version is already main, a request nobody spent lapses after 24 hours or when Foreman is current, and a verified hand-install clears it and starts the window from its own finish time. `self-upgrade status` shows `urgent`, `lastFinishedAt`, `nextInstall` and `batchDueAt`. The drain bound (`drain_max_minutes`, default 30) is measured from the first tick of a continuous hold, and a newer main during the hold does not restart it, so merges cannot extend a hold without bound. The dashboard version pill and the "behind main" item say "merged, not installed" and "Next install: <time or why>". The wait for the live tick that verifies an install is unchanged (see the open note in the pull request).

## Bootstrap installer (issue #101)
`tools/bootstrap-install.sh` is the one part of the supervisor that cannot install itself. Everything else, including the upgrader (`supervisor/upgrade.mjs`, `tools/upgrade-supervisor.sh`, `tools/rollback-supervisor.sh`), installs through it like any other reviewed change, through the same review-gated eligibility (D-011/D-021). A range that changes the bootstrap itself is refused with a needs-homeowner alert; the homeowner installs it by hand.

### Installing a refused update: `self-upgrade hand-install SHA` (issue #446)
The alert and the dashboard's Needs you item give the full commit and the exact command: `/root/bin/ai-supervisor self-upgrade hand-install <40-character SHA>`. It runs eight phases and prints one progress line each, then one final `RESULT:` line (exit 0 only for `installed`):
1. Hold: writes `team/hand-install.hold`. While it is live the team tick starts nothing, the self-upgrade step does nothing, and the reconciler restarts no paused or queued job (`enabled: false` stops only the team loop; the reconciler runs before that check). A due restart keeps its record, is reported as `held` by `reconcile`, and restarts on the first reconcile after the hold ends. `team.local.json` is never edited. The hold is live only while its process runs and for at most 3 hours, so a crash cannot hold the team.
2. Drain running jobs, bounded by `self_upgrade.drain_max_minutes`. If a job still runs at the bound nothing is changed and new starts resume.
3. Install through the bootstrap route on that exact SHA, using the installer from that commit (validator and full tests). A failing test is named and nothing is swapped.
4. Dry-run tick on the new version. 5. Dashboard restart by the normal route, then a local answer check and, when `self_upgrade.public_dashboard_url` is set in `team.local.json`, a public one (otherwise the output says the public check was not configured). 6. The hold is released. 7. A live tick on the new version.
Any failure after the swap rolls back with `rollback-supervisor.sh`, restarts the dashboard on the old version and confirms the installed commit is the old one (otherwise `rollback-failed`, manual repair). The hold is always released, also on an error. `team/hand-install.json` records the phase: a later run (or the same command again) first rolls back an unverified swap left by a run that died.

Every install: (1) a clean clone of the exact merged commit from the `origin` URL (GitHub), never a local checkout, verified to be that commit with no local changes; (2) `tools/validate-project.mjs` and the full tests in that copy; (3) the atomic swap (`tools/upgrade-supervisor.sh`); (4) the dry-run tick and then the next live tick as health checks; (5) automatic rollback if any of these fails, with the rollback latch. The bootstrap script is read from the installed commit, so a payload cannot replace the installer that checks it.

Exit codes: `10` transient (clone, fetch or checkout failed), `11` validator or tests failed, `12` payload differs from the reviewed commit, `13` swap failed. A transient failure, including GitHub being unreachable, never latches a commit: it is retried with backoff (10 minutes, doubling to 4 hours) and raises no alert on its own. A failed validator or test run blocks only that commit until a newer main, with one alert. Issue #581: that commit gets one more attempt after 30 minutes (`PRECHECK_RETRY_MS`) without waiting for main to move; a second failure latches it until a newer main. The enable gate (`tools/verify-reconcile-env.sh`) runs its dry-run tick and plan check twice before it refuses, and its failure text includes the tick's stderr and the plan check's own reason.

`team status` (an `installer:` line) and the Supervisor page's Version card show the installed version, the last install result (`installed`, `verified`, `transient`, `blocked`, `needs-homeowner`, `rolled_back`, `rollback_failed`) and the next attempt. The same data is the `install` object in `team/self-upgrade.json` for #105's Install stage.

### Applying a needed local setting (issue #853)
When a merged change needs a host-specific local setting (see "A change that needs a local setting" in [team-loop.md](team-loop.md)), the dashboard shows one Needs you card, "Apply setting <key> = <value> needed by PR #N", with the exact value and Approve and Reject buttons. The buttons use the same `/inbox` write route and protections as the overseer's proposals (Host, Origin, secret proof, cooldown; D-029), so the click must come from the listen address or an already allowed origin. When a cross-origin write is refused and its Origin is the one awaiting approval, the refusal page links to the card on the listen address, because an approval from the refused origin would be refused again. Only the first valid refused Origin after install fills the item, and the homeowner sees the value before approving; any LAN client can cause a refused request, so an unexpected value is rejected, not approved. Approval records the decision only; the next tick backs up `team.local.json`, merges the value, checks the file parses and validates, and records the result.

### Dashboard public address (issue #556)
A dashboard write (Watch, Mark as read, Refresh allowance, Approve or Reject on an inbox proposal, and the circuit breaker's Resume) is accepted only when its `Origin` is the listen address or is listed exactly in `dashboard.allowed_origins` in `team.local.json`, for example `{"dashboard": {"allowed_origins": ["https://agents.example.org"]}}` (scheme and host, optional port, no path or wildcard). The `Host` must still be the listen address, so the reverse proxy must forward the upstream Host. The access proof is still required, and Resume still needs a person's click (`Sec-Fetch-Site`, `Sec-Fetch-User`). A refused request, including a missing or stale access proof or an oversized body, shows a page naming the Origin and Host received and a link back; no state changes. Entries must be lowercase. Each refusal is also logged on the server (`dashboard: write refused`, with the Origin, Host and path received), which is how to capture the values the proxy sends. The list is read on every request, so no dashboard restart is needed after editing `team.local.json`; if an edit is invalid (for example an uppercase entry), the dashboard keeps using the previous list and shows the configuration error banner (a restart is needed only to deploy this change). Forwarding headers (`X-Forwarded-Host`, `X-Forwarded-Proto`) are ignored: only `Origin` and the upstream `Host` are checked. If the proxy forwards the public Host instead of the listen `host:port`, writes are refused with 421 until the proxy is set to forward the upstream Host.
