# Foreman MCP server (read-only, for the overseer)

Issue #569, decision D-030 (an agent proposal until the homeowner approves it). A small stdio MCP server that lets the overseer read Foreman's state from Claude desktop, over SSH to a restricted Tower account. It reads, with one exception: the inbox (issue #124, D-031 proposed, below), where it can only propose items for the homeowner to approve on the dashboard.

## What it is
- `foreman-mcp/` holds the server: `server.mjs` (stdio entry), `protocol.mjs` (JSON-RPC and MCP), `tools.mjs`, `source.mjs`, `redact.mjs`, `calllog.mjs` and `launcher.sh`. It imports nothing from `supervisor/` and uses no npm packages.
- It is a separate process from the dashboard. It reads the dashboard's existing `/api/view.json` (a GET, cached for 20 seconds, capped at 48 MB, 10 second timeout) and `/proc`. The account cannot read Foreman's state directory, and nothing widens that.
- Tools: `foreman_status`, `foreman_review_order` (the planner's own queue, with the reason each pull request waits, is held or is not queued), `foreman_why_blocked` (a PR or an issue), `foreman_jobs` (records, tokens and cost; no transcripts), `foreman_plan`, `foreman_host` (load, memory and swap), `foreman_reports` (reports left by hand-run sessions; see below), `foreman_job_outcome` and `foreman_discarded` (see below), `foreman_rebase_stats` (see below), `foreman_mismatches` and `foreman_needs_you` (see below), `foreman_installs` and `foreman_breaker_history` (see below), `foreman_diagnostics`, `foreman_waste`, `foreman_config` and `foreman_budget` (see below).
- There is no live planner dry run. `team tick --dry-run` needs the state root, which the account cannot read, and may contend for the tick lock. `foreman_plan` shows the plan the dashboard recomputes with `team.plan()` on each request, from the last tick's cached GitHub data (cached about 20 s). It does not pass through the circuit breaker, so while the breaker is halted `plannedActions` may list actions a real tick would drop; the result carries `breakerHalt` to say so (with `count` and `entries` when several causes are halted, and `error` if breaker evaluation failed). `foreman_jobs` never returns a transcript, only `transcriptAvailable`. `foreman_host` omits `memoryPressure` when the kernel has no `/proc/pressure` (Tower's has none).
- Live acceptance (G8, after install, recorded on the real account, still open): the tools callable from a linked cloud session through the ssh entry, one `tools/list` from the desktop, and the key gets no shell, no other command, no pty and no forwarding. A throwaway-sshd check of the documented `restrict,command=...` line showed a client command ignored, pty and `-L` refused, and sftp refused.
- Output is capped at 24,000 characters per result and 30 calls a minute. Secret-shaped text (tokens, keys, `Bearer` values, URL passwords, `password=` pairs, private keys) is replaced by `[redacted]` in every result and in the call log. No model is called and no usage is spent. Cost figures are the provider CLI's usage estimates, not charges.
- Every call is logged (time, tool, redacted arguments, duration, outcome) to the account's own file, rotated at 256 KB. That is the only file it writes. The launcher runs Node with `--permission`, so reads are limited to the server directory, `/proc`, the configuration file and the log directory, and writes to the log directory only.

## Job outcome and discarded results (`foreman_job_outcome`, `foreman_discarded`, issue #623)
The overseer could not see why a job ended without its post-condition, or which paid results were thrown away: the job records, events, transcripts and dispatcher state sit in the state root, which the account cannot read. Nothing about that access changes. **The one new read route** is two more GET paths on the dashboard the server already reads (same host check, GET only, no write, no new port, no new account permission): `/api/jobs/<32 hex>/outcome.json` and `/api/discarded.json`, served by `supervisor/joboutcome.mjs`. The MCP server calls them at the same address as `viewUrl`; no `launcher.env` or permission-flag change is needed.
- **`foreman_job_outcome`** (`id`: the full job id, or a unique prefix of at least 6 characters taken from the recent jobs in the view): the scope line the job was created with (not the full prompt), status, attempts, last event, start and end, the post-condition and, when it did not hold, the cause and detail Foreman recorded; tool-call counts and the last assistant message from the end of the transcript (read from the last 256 KB only); `pushed`, which is evidence rather than a remote check (head at start, last checkpoint head, whether it moved, uncommitted file count, `git push` commands seen in the log tail); cost (usage equivalent); the last 15 non-checkpoint events; and a log tail of the last 25 transcript entries, each cut to 300 characters.
- **`foreman_discarded`** (optional `limit`, default 50, at most 200): the circuit breaker's waste record, which is every finished job that spent tokens and left no usable result (a review whose verdict was refused at ingestion, a review that ended with no verdict, a job that failed after spending), newest first, with the cause, the PR or issue, the model, tokens and cost, plus totals. It covers the last 7 days and at most 1,000 records (the breaker's own retention). Cost is the provider CLI's usage estimate, not a charge.
- Both are read-only, bounded and redacted twice (by the dashboard, then by the server), make no model call and take no lock. The tests assert that seeded secret-shaped text never appears, that the state tree is unchanged and that other methods are refused (`node --test tests/foreman-job-outcome.test.mjs`). After deploying the dashboard change, restart the dashboard and copy the updated `foreman-mcp/` directory as in the install steps; until the dashboard is updated the two tools answer that the dashboard returned HTTP 404.

## Install history and breaker history (`foreman_installs`, `foreman_breaker_history`, issue #625)
On 5 Nov 2026 an install failure and two breaker trips had to be pieced together from several places. Same route pattern as #623: **two more GET paths on the dashboard the server already reads** (same host check, GET only, no write, no new port, no new account permission): `/api/installs.json` and `/api/breaker.json`, served by `supervisor/installs.mjs`. No `launcher.env` or permission change; until the dashboard is restarted on the new version the tools answer HTTP 404.
- **`foreman_installs`** (optional `limit` on the records, default 15, at most 40): installed commit against main and how far behind; the next install and why it waits; whether an install is **draining** (target, since when, jobs still running); the last install attempt, with the **failing test names**, a redacted excerpt and whether it was retried (#581); a rollback latch and a refusal; the **running version per process** (Foreman, dashboard, workers) with `matchesInstalled`; and the newest install records (result, failed flag, PRs, reason, checks). Process versions are read from each process command line under `versions/<sha>/`; the command line, environment and arguments are never returned. Evidence, not a remote check.
- **`foreman_breaker_history`** (optional `limit`, default 20, at most 100): each trip, newest first, with its cause (scope), what tripped it, the wasted jobs and the PRs and issues, tokens and cost (usage equivalent, not a charge), when it tripped and when it cleared, or `stillHalted`. The breaker now keeps one `history` entry per trip in its state (at most 100); figures follow the halt while held and stop when it is cleared. A halt that predates this record is shown from the halt in force, with no cleared time; earlier cleared trips were not recorded and are not invented.
- Read-only, bounded and redacted twice (dashboard, then server), no model call, no lock. Tests: `node --test tests/foreman-installs.test.mjs` (positive and negative cases, a stale process version, the history cap, GET-only routes, an unchanged state tree, and no secret-shaped output with fixtures built at run time). Deploy: restart the dashboard on the new version and copy `foreman-mcp/` as in the install steps.

## Diagnostics, waste, config and budget (`foreman_diagnostics`, `foreman_waste`, `foreman_config`, `foreman_budget`, issue #635)
On 5 Nov 2026 the overseer had to ask for each of these by hand while working out why Claude was held in `reviews_only` and why the breaker had halted reviews. Three more GET paths on the dashboard the server already reads (same host check, GET only, no write, no new port, no new account permission): `/api/diagnostics.json`, `/api/waste.json` and `/api/config.json` (`supervisor/mcpreads.mjs`, and the existing `diagnosticsData`). Until the dashboard is restarted on the new version those three tools answer HTTP 404. `foreman_budget` reads the view the server already fetches.
- **`foreman_diagnostics`**: the data behind the dashboard's Diagnostics tab (see `docs/dashboard.md`), for the last 7 days: tick gaps and late ticks, job turnaround, verdict lag, idle time by cause, pass statistics, the wake state and the host recorder summary by day. The recorder's hourly samples are left out (their count is given); long lists are shortened to the output limit and say so.
- **`foreman_waste`** (optional `days`, 1 to 30, default 7): tokens and cost (usage equivalent, not a charge) of jobs that spent and left no usable result, grouped by failure cause in total and per UTC day, newest day first. It is built from the breaker's waste record, which holds the last 7 days and at most 1,000 entries, so a longer span shows no more.
- **`foreman_config`**: the configuration Foreman uses now (shipped `team.json` plus the `team.local.json` override) and `differences`: every setting whose effective value is not the shipped default, by dotted path, with both values. A secret-named key loses its value, an alert command keeps its program and the number of arguments removed, and every string is redacted. If the local file is invalid the last good configuration is shown with the error.
- **`foreman_budget`**: per agent, the mode and **why** it holds (`why`, `heldJobTypes`), when it **ends** (`endsAt`), the weekly window (used, reset time, hours left), the **rate** behind the estimate (`perHour`, and whether it is the recent rate or the window average), the estimate at reset and when the agent would run out (for information only: since issue #680 they never set a mode), the short window, typical job costs and the thresholds from the effective configuration.
- Read-only, bounded and redacted twice, no model call, no lock. Tests: `node --test tests/foreman-reads1.test.mjs` (grouping and span, damaged records, the configuration difference against the real shipped file, GET-only routes, an unchanged state tree and no secret-shaped output, with fixtures built at run time).

## Mismatches and grouped Needs you (`foreman_mismatches`, `foreman_needs_you`, issue #624)
On 5 Nov 2026 the Needs you list had 54 items, most of one cause. Both tools are pure readings of the `/api/view.json` the server already fetches (`foreman-mcp/insights.mjs`): no new route, no new permission, no model call, no lock. Output goes through the same redaction and 24,000 character bound as every tool, and lists are capped at 40 with the true count stated.
- **`foreman_needs_you`**: the Needs you items grouped by the cause part of the item id (`homeowner-pr-538` and `homeowner-pr-540` are cause `homeowner-pr`), most items first: count, the pull requests or issues involved, one example and the action asked (the most common up to three), plus `totalItems` and `distinctCauses`.
- **`foreman_mismatches`**: four kinds, each with the evidence. `implemented-without-pr` (the issue's queue reason says it started earlier with no PR, and no open PR or running job names it); `finished-not-recorded` (a review job's verdict was refused or never recorded, from the Needs you cards); `stale-label` (a closed issue still labelled needs-homeowner, or an open PR with the label, no Needs you item and not awaiting review); `hold-by-old-job` (#583: the card says a stopped job holds the label, but a newer job has run on the PR since, or the held job started over 24 hours ago). These are heuristics over the view and the remote is not checked: an empty result means none of the four is visible. A job that finished but was never recorded at all cannot be seen from the view and is not claimed.
- Tests: `node --test tests/foreman-insights.test.mjs` (positive and negative cases for each kind, the bound, read-only annotations, and no secret-shaped output with fixtures built at run time). Deploy by copying the `foreman-mcp/` directory as in the install steps; no dashboard change is needed.

## Rebase treadmill measure (`foreman_rebase_stats`, issue #633)
The behaviour half of the issue: a conflict rebase is deferred while another open, non-conflicting pull request is ahead in the review or merge queue (green and unreviewed with an agent able to review it, or holding a PASS that GitHub does not report BLOCKED; a needs-homeowner, decision-held, BLOCKED or unreviewable pull request is not ahead), and starts once nothing is ahead, so the pull request is rebased just before its review or merge rather than on every main move (#633; `rebaseNotNext` in `supervisor/team.mjs`, `tests/rebase-starvation.test.mjs`). A behind-with-PASS rebase is not deferred. A PASS carries across a clean, green rebase whose range-diff shows an identical patch, message and placement, while any difference needs a new review (D-025; `tests/rebase-carry.test.mjs`, `tests/rangediff-placement.test.mjs`, `tests/rebase-safety.test.mjs`). This tool adds the measurement.
- **`foreman_rebase_stats`** (optional `splitAt`, an ISO date or time, and `limit`, default 100, at most 200): for the merged pull requests in the dashboard view, the rebases per pull request, the reviews per pull request (verdicts a review produced; D-025 carried verdicts are not reviews and are reported apart as `carried`) and the time from first recorded activity to merge (mean and median). With `splitAt` the figures are given for merges before and after it, so set it to the day a rebase-policy change was deployed. Open time is measured from the first job or verdict the view holds (the merge entry itself is not counted), not the GitHub creation time, and a pull request with no timestamp is left out of the time figures only.
- Read-only, a pure reading of `/api/view.json`: no new route, no model call, no lock, same redaction and 24,000 character bound. Tests: `node --test tests/foreman-insights.test.mjs` (averages, split, empty and bad input, no secret-shaped output with fixtures built at run time).

## Session reports (`foreman_reports`, issue #612)
Hand-run Tower sessions can leave a final report for the overseer in one fixed folder, so the homeowner no longer carries it by hand. Raw session logs are never exposed: they can hold secrets. With no argument the tool lists the reports (name, time, size), newest first; with a name it returns that one report as text.
- **Folder:** `reportsDir` in the server configuration (and `REPORTS_DIR` in `launcher.env`, which gives the launcher read access to it). Create it owned by root with group `foreman-mcp`, directory mode 750, files mode 640 (group-readable). Only the owner writes. The server never writes there.
- **Names:** one path component, letters, digits, dot, dash and underscore, at most 80 characters, ending `.md` or `.txt`, and not starting with a dot. Anything else, including separators, `..`, absolute paths and encoded forms, is refused. Files that do not match are not listed.
- **Symbolic links** are never followed: they are not listed, and opening one is refused (`O_NOFOLLOW`).
- **Size:** at most 256 KB is read from a file; a result over the output limit (24,000 characters) is cut with a marker `[truncated: N more characters not shown]`. The existing secret redaction is applied to the text, and each call is logged like every other tool.

## Install (on Tower, as root; needs the homeowner's approval of D-030)
1. Copy `foreman-mcp/` to a persistent directory owned by root and read-only to the account, outside every Foreman checkout and not on the RAM disk, for example `<install dir>/foreman-mcp`. Record the commit it came from in a `VERSION` file beside it.
2. Write the configuration, owned by root and readable by the account: `{ "viewUrl": "http://<dashboard host>:<port>/api/view.json", "logFile": "<account home>/logs/calls.log", "reportsDir": "<reports folder>" }` (`reportsDir` is the folder described in the reports section above; leave it out only if `foreman_reports` is not wanted). Use the address the dashboard serves on; it is not kept in Git.
3. Write `launcher.env` beside `launcher.sh`: `NODE_BIN=<absolute node>`, `CONFIG_FILE=<configuration file>`, `LOG_DIR=<account home>/logs`, and `REPORTS_DIR=<reports folder>` (the same folder as `reportsDir`; it gives the launcher read access to it).
4. Create the account `foreman-mcp`: locked password, its own home, no extra groups, and a login shell that can run the forced command (for example `/bin/sh`). Create the log directory owned by the account, mode 0700.
5. Put one line in `<account home>/.ssh/authorized_keys` (home mode 0755 or tighter and owned by root or the account, `.ssh` 0700, file 0600, all owned by the account):
   `restrict,command="<absolute path>/launcher.sh" ssh-ed25519 <public key> <comment>`
   `restrict` turns off the pty, port, agent and X11 forwarding and `~/.ssh/rc`, and the forced command ignores whatever the client asks to run.
6. If sshd uses `AllowUsers` or `AllowGroups`, the account must be listed. Check with `sshd -T` (read-only); do not reload sshd without the homeowner.

## Claude desktop configuration
In Claude desktop's MCP configuration, add a server that runs `ssh` and speaks MCP over its stdin and stdout, with placeholders for your values:
```
{ "mcpServers": { "foreman": { "command": "ssh", "args": ["-i", "<path to the private key>", "-o", "IdentitiesOnly=yes", "-o", "BatchMode=yes", "foreman-mcp@<tower host>"] } } }
```
The server works only while the computer and Claude desktop are running. Nothing is exposed to the internet and no listening port is added.

## Revoke access
Remove the one line from `<account home>/.ssh/authorized_keys`, or lock the account (`usermod -L foreman-mcp`), or delete it (`userdel foreman-mcp`). Remove the server directory and the configuration if the server is retired. On Unraid, also remove the line that recreates the account from `/boot/config/go` and the script it runs.

## The inbox (issue #124, D-031 proposed)
The overseer can propose; only the homeowner can approve. This is the one write the server has, and it goes into one directory.

- **Tools.** `foreman_propose` (kind `prompt` or `issue_draft`, a title, the text, an optional reason) and `foreman_proposal_status` (the state and result of one item). They appear only when an inbox directory is configured. There is no tool that approves, rejects or runs anything.
- **Layout.** `<inbox>/items/<id>.json` is written by the `foreman-mcp` account (the server picks the 32-hex-character name; a call cannot name a path). `<inbox>/status/<id>.json` and `<inbox>/audit.jsonl` are written only by Foreman (root) and readable by the account. The launcher gives Node write permission to `<inbox>/items` only, so the server cannot touch `status/`, the audit log or anything else.
- **What Foreman does with an item** (each tick, so allow up to five minutes before a card appears). It reads only regular files of at most 32 KB, validates the shape, refuses unknown kinds and fields, text over 8,000 characters (title 200), control characters, secret-shaped text and AI-attribution text, and allows at most 10 items waiting at once. A refused item records the reason (never the text) in its status. Each valid item becomes one Approve/Reject card in Needs you, showing the exact text. The card is bound to a hash of the file: an item edited after pickup is refused at approval and again at use.
- **Approve and reject.** The card posts to the dashboard's `/inbox` route, protected like the other dashboard writes (D-029): Host, Origin, the secret proof in the state root, and a one-second cooldown. Reject records it and does nothing. Approve is recorded; the next tick acts.
- **An approved prompt** starts one ordinary job (kind `inbox`) in its own worktree and branch `<prefix>inbox-<id8>`, in an implementer slot, under the same allowance, usage-limit, breaker and model rules as an implement job. It never writes as Opus. The prompt text is passed as quoted task data, and the limits (no merge, no approval, no verdict, no review bypass) are stated before and after it. The job writes a short summary to a file Foreman gives it; Foreman redacts it and records it as the item's `result`.
- **An approved issue draft** is posted by the tick as the homeowner's GitHub account, redacted, after a final secret and attribution check. The state `posting` is recorded before the post and a marker comment in the body is looked up first, so it is posted once.
- **Actions (issue #629, D-033 proposed).** `foreman_propose` also accepts kind `action` with a title, `action` (`new_review_attempt` + PR number, `reopen` + issue number, `close_job`, `stop_job`, `resume_job` + the 8-character job id from the dashboard) and a `reason` (at most 300 characters). Nothing else is accepted: no command, path or free text target. The card names the action and its target; after the homeowner approves it, the next tick re-checks the target and either does it once or ends the item `failed` with the reason and nothing changed. Refusals: `new_review_attempt` with attempts left, a verdict or a running review; `reopen` as `team reopen`; `close_job` unless the job is blocked, failed or stopped and its PR has a newer head, and unless its worktree was saved (uncommitted work is committed and pushed to `saved/<job>-<branch>`; ignored files are not) and git shows nothing unsaved; `stop_job` of an ended job; `resume_job` of a job on an overtaken head, an agent out of allowance or a full provider role. An agent job cannot approve: approval exists only on the dashboard route.
- **Audit.** `<inbox>/audit.jsonl` has one line per event (time, id, event, kind, SHA-256 of the item). No content and no secrets. Finished items and their status are removed after 14 days.
- **Statuses** (`foreman_proposal_status`): `waiting` (not yet picked up), `pending`, `refused`, `rejected`, `approved`, `running`, `posting`, `done`, `failed`.

### Install the inbox (on Tower, as root; needs the homeowner's approval of D-031)
1. Create the inbox directory outside the Foreman state root and outside every checkout, owned by root and readable by the account: `<inbox>` mode 0755, `<inbox>/status` root-owned 0755, `<inbox>/items` owned by `foreman-mcp` mode 0700. Foreman (root) reads and writes everywhere in it.
2. Add `"inboxDir": "<inbox>"` to the server configuration file, and `INBOX_DIR=<inbox>` to `launcher.env`. Copy the updated `foreman-mcp/` directory (including `inbox.mjs`) and record the commit in `VERSION`.
3. Add `"inbox": { "dir": "<inbox>" }` to `team.local.json`. Without it Foreman ignores the inbox and the dashboard has no `/inbox` route. Restart the dashboard server so it reads the setting.
4. Check as the account (`ssh foreman-mcp@<tower>` through the forced command): `tools/list` shows the two new tools; a proposal appears in `items/`.

### Trial account and revoking access
The trial account's key and forced command are unchanged by this feature. To stop proposals but keep reads: remove `INBOX_DIR` from `launcher.env` and `inboxDir` from the configuration (the tools disappear), or remove the `inbox` block from `team.local.json` (Foreman stops reading the inbox and the route disappears). To revoke everything: remove the one `authorized_keys` line, lock or delete the account, as above. Items already approved but not yet started stop being planned when the `inbox` block is removed.

### Tests
`node --test tests/foreman-inbox.test.mjs`: validation, refusal before a card, the pending cap, tamper detection, reject and approve, the audit log without content, the MCP tools and the permission flags (writes to `items/` only; `status/` and everywhere else denied), the card and the write protection, and the team side (planning, limits, no Opus, results written back, an issue draft posted once without attribution).

## Checks
`node --test tests/foreman-mcp.test.mjs` covers the protocol, agreement with the planner's order, the proof that it cannot modify Foreman state (a fake state tree is byte-for-byte unchanged, only GETs reach the dashboard, and the permission model refuses other writes), bounded output, and no secret-shaped output. The restricted-key check required by #569 (no shell, no other command, no pty, no forwarding, tools callable over SSH) is a recorded manual check on the host.
