# Foreman MCP server (read-only, for the overseer)

Issue #569, decision D-030 (an agent proposal until the homeowner approves it). A small stdio MCP server that lets the overseer read Foreman's state from Claude desktop, over SSH to a restricted Tower account. It reads, with one exception: the inbox (issue #124, D-031 proposed, below), where it can only propose items for the homeowner to approve on the dashboard.

## What it is
- `foreman-mcp/` holds the server: `server.mjs` (stdio entry), `protocol.mjs` (JSON-RPC and MCP), `tools.mjs`, `source.mjs`, `redact.mjs`, `calllog.mjs` and `launcher.sh`. It imports nothing from `supervisor/` and uses no npm packages.
- It is a separate process from the dashboard. It reads the dashboard's existing `/api/view.json` (a GET, cached for 20 seconds, capped at 48 MB, 10 second timeout) and `/proc`. The account cannot read Foreman's state directory, and nothing widens that.
- Tools: `foreman_status` (also `infraFaults`: infrastructure faults and parked agents, issue #1107; `hostPressure`: the hold in force and each measure next to its threshold, issue #1151), `foreman_review_order` (the planner's own queue, with the reason each pull request waits, is held or is not queued), `foreman_why_blocked` (a PR or an issue; for an issue also `dependencies`: `dependsOn`, `blockedBy`, `unlocks`, issue #1103), `foreman_jobs` (records, tokens and cost; no transcripts), `foreman_plan`, `foreman_host` (load, memory and swap; swap activity, disk wait and top processes by memory), `foreman_tests`, `foreman_ticks`, `foreman_item_timeline` (issue #636), `foreman_reports` (reports left by hand-run sessions; see below), `foreman_stop_record` (the homeowner stop record a latch or pause names; see below), `foreman_job_outcome` and `foreman_discarded` (see below), `foreman_rebase_stats` (see below), `foreman_mismatches` and `foreman_needs_you` (see below), `foreman_installs` and `foreman_breaker_history` (see below), `foreman_diagnostics`, `foreman_waste`, `foreman_config` and `foreman_budget` (see below).
- There is no live planner dry run. `team tick --dry-run` needs the state root, which the account cannot read, and may contend for the tick lock. `foreman_plan` shows the plan the dashboard recomputes with `team.plan()` on each request, from the last tick's cached GitHub data (cached about 20 s). It does not pass through the circuit breaker, so while the breaker is halted `plannedActions` may list actions a real tick would drop; the result carries `breakerHalt` to say so (with `count` and `entries` when several causes are halted, and `error` if breaker evaluation failed). `foreman_jobs` never returns a transcript, only `transcriptAvailable`. `foreman_host` omits `memoryPressure` when the kernel has no `/proc/pressure` (Tower's has none).
- Live acceptance (G8, after install, recorded on the real account, still open): the tools callable from a linked cloud session through the ssh entry, one `tools/list` from the desktop, and the key gets no shell, no other command, no pty and no forwarding. A throwaway-sshd check of the documented `restrict,command=...` line showed a client command ignored, pty and `-L` refused, and sftp refused.
- Output is capped at 24,000 characters per result and 30 calls a minute. Secret-shaped text (tokens, keys, `Bearer` values, URL passwords, `password=` pairs, private keys) is replaced by `[redacted]` in every result and in the call log. No model is called and no usage is spent. Cost figures are the provider CLI's usage estimates, not charges.
- Every call is logged (time, tool, redacted arguments, duration, outcome) to the account's own file, rotated at 256 KB. That is the only file it writes. The launcher runs Node with `--permission`, so reads are limited to the server directory, `/proc`, the configuration file and the log directory, and writes to the log directory only.

## Why an open issue is not running (issue #1121)
`foreman_plan` returns, with each planned action, `lastTick`: the outcome the last tick recorded for it (`launched`, `held` with its kind and one reason, or `not recorded` for an action planned since), and `foreman_why_blocked` returns the same records for the item as `lastTick` (issue #1223). `foreman_why_blocked` for an issue returns `assignment`: the agent and model it goes to, the `rule` that chose them (the agent's `issues` list and position, the unblock queue, or the unlisted pool taken in number order by the first agent with a free slot), the `rank`, and the specific `wait` (`kind`: dependency, homeowner, agent-paused with `until`, allowance, reserve, cap, held, busy, not-admitted, or running, pr-open, next). An open issue with no implementer and no stated reason has `fault` set; `foreman_status` lists them as `assignmentFaults` and the dashboard raises a warning. The `idle` text in `foreman_status` names the rule that leaves the agent idle. Source: `supervisor/issueassign.mjs` (view field `assignments`). Read-only; it only makes the current behaviour visible.

## Job outcome and discarded results (`foreman_job_outcome`, `foreman_discarded`, issue #623)
The overseer could not see why a job ended without its post-condition, or which paid results were thrown away: the job records, events, transcripts and dispatcher state sit in the state root, which the account cannot read. Nothing about that access changes. **The one new read route** is two more GET paths on the dashboard the server already reads (same host check, GET only, no write, no new port, no new account permission): `/api/jobs/<32 hex>/outcome.json` and `/api/discarded.json`, served by `supervisor/joboutcome.mjs`. The MCP server calls them at the same address as `viewUrl`; no `launcher.env` or permission-flag change is needed.
- **`foreman_job_outcome`** (`id`: the full job id, or a unique prefix of at least 6 characters taken from the recent jobs in the view): the scope line the job was created with (not the full prompt), status, attempts, last event, start and end, the post-condition and, when it did not hold, the cause and detail Foreman recorded; tool-call counts and the last assistant message from the end of the transcript (read from the last 256 KB only); `pushed`, which is evidence rather than a remote check (head at start, last checkpoint head, whether it moved, uncommitted file count, `git push` commands seen in the log tail); cost (usage equivalent); the last 15 non-checkpoint events; and a log tail of the last 25 transcript entries, each cut to 300 characters.
- **`foreman_discarded`** (optional `limit`, default 50, at most 200): the circuit breaker's waste record, which is every finished job that spent tokens and left no usable result (a review whose verdict was refused at ingestion, a review that ended with no verdict, a job that failed after spending), newest first, with the cause, the PR or issue, the model, tokens and cost, plus totals. Fields that are null are left out of each item to save space. If that many entries would not fit the 24,000-character output limit, fewer are returned (`shown` equals the list length) and the result carries `truncated` and a note; if even a single entry is too large for the limit, zero entries are returned with the note 'not even one entry fits the output limit'. It covers the last 7 days and at most 1,000 records (the breaker's own retention). Cost is the provider CLI's usage estimate, not a charge.
- Both are read-only, bounded and redacted twice (by the dashboard, then by the server), make no model call and take no lock. The tests assert that seeded secret-shaped text never appears, that the state tree is unchanged and that other methods are refused (`node --test tests/foreman-job-outcome.test.mjs`). After deploying the dashboard change, restart the dashboard and copy the updated `foreman-mcp/` directory as in the install steps; until the dashboard is updated the two tools answer that the dashboard returned HTTP 404.

## Install history and breaker history (`foreman_installs`, `foreman_breaker_history`, issue #625)
On 5 Nov 2026 an install failure and two breaker trips had to be pieced together from several places. Same route pattern as #623: **two more GET paths on the dashboard the server already reads** (same host check, GET only, no write, no new port, no new account permission): `/api/installs.json` and `/api/breaker.json`, served by `supervisor/installs.mjs`. No `launcher.env` or permission change; until the dashboard is restarted on the new version the tools answer HTTP 404.
- **`foreman_installs`** (optional `limit` on the records, default 15, at most 40): installed commit against main and how far behind; the next install and why it waits; whether an install is **draining** (target, since when, jobs still running); the last install attempt, with the **failing test names**, a redacted excerpt and whether it was retried (#581); a rollback latch and a refusal; the **running version per process** (Foreman, dashboard, workers) with `matchesInstalled`; and the newest install records (result, failed flag, PRs, reason, checks). Process versions are read from each process command line under `versions/<sha>/`; the command line, environment and arguments are never returned. A process started through the `current/` symlink is shown with the version `current/` resolves to when read, not the version it loaded, so a long-lived such process started before an install would wrongly show `matchesInstalled` true; on the live host only the short-lived reconcile tick uses `current/`. Evidence, not a remote check.
- **`foreman_breaker_history`** (optional `limit`, default 20, at most 100): each trip, newest first, with its cause (scope), what tripped it, the wasted jobs and the PRs and issues, tokens and cost (usage equivalent, not a charge), when it tripped and when it cleared, or `stillHalted`. The breaker now keeps one `history` entry per trip in its state (at most 100); figures follow the halt while held and stop when it is cleared. A halt that predates this record is shown from the halt in force, with no cleared time; earlier cleared trips were not recorded and are not invented.
- Read-only, bounded and redacted twice (dashboard, then server), no model call, no lock. Tests: `node --test tests/foreman-installs.test.mjs` (positive and negative cases, a stale process version, the history cap, GET-only routes, an unchanged state tree, and no secret-shaped output with fixtures built at run time). Deploy: restart the dashboard on the new version and copy `foreman-mcp/` as in the install steps.

## Diagnostics, waste, config and budget (`foreman_diagnostics`, `foreman_waste`, `foreman_config`, `foreman_budget`, issue #635)
On 5 Nov 2026 the overseer had to ask for each of these by hand while working out why Claude was held in `reviews_only` and why the breaker had halted reviews. Three more GET paths on the dashboard the server already reads (same host check, GET only, no write, no new port, no new account permission): `/api/diagnostics.json`, `/api/waste.json` and `/api/config.json` (`supervisor/mcpreads.mjs`, and the existing `diagnosticsData`). Until the dashboard is restarted on the new version those three tools answer HTTP 404. `foreman_budget` reads the view the server already fetches.
- **`foreman_diagnostics`**: the data behind the dashboard's Diagnostics tab (see `docs/dashboard.md`), for the last 7 days: tick gaps and late ticks, job turnaround, verdict lag, idle time by cause, pass statistics, the wake state and the host recorder summary by day. The recorder's hourly samples are left out (their count is given); long lists are shortened to the output limit and say so.
- **`foreman_waste`** (cost fields are in pounds, `costGbpEquivalent`; see docs/dashboard.md, issue #1097) (optional `days`, 1 to 30, default 7): tokens and cost (usage equivalent, not a charge) of jobs that spent and left no usable result, grouped by failure cause in total and per UTC day, newest day first (each day lists its top 5 causes plus one remainder row). It is built from the breaker's waste record, which holds the last 7 days and at most 1,000 entries, so a longer span shows no more.
- **`foreman_failure_causes`** (issue #1020; optional `days`, 1 to 14, default 7): every failed job's recorded cause from a fixed list (environment, wedged, deterministic, review disagreement, prerequisite open, identity or evidence, Foreman bug, provider limit, homeowner decision needed, unclassified) with tokens, cost and the items involved, for the last 24 hours, the last 7 days and per UTC day, top causes by waste first. `foreman_status` shows the top five as `breaker.topFailureCauses`.
- **`foreman_config`**: the configuration Foreman uses now (shipped `team.json` plus the `team.local.json` override) and `differences`: every setting whose effective value is not the shipped default, by dotted path, with both values. A secret-named key (matched on whole name segments, so `chain_passes` and `max_tokens` are kept) loses its value, an alert command keeps its program and the number of arguments removed, and every string is redacted. If the local file is invalid the last good configuration is shown with the error.
- **`foreman_budget`**: per agent, the mode and **why** it holds (`why`, `heldJobTypes`), when it **ends** (`endsAt`), the weekly window (used, reset time, hours left), the **rate** behind the estimate (`perHour`, and whether it is the recent rate or the window average), the estimate at reset and when the agent would run out (for information only: since issue #680 they never set a mode), the short window, typical job costs and the thresholds from the effective configuration.
- Read-only, bounded and redacted, no model call, no lock. Waste, configuration and budget are redacted twice (dashboard, then server); diagnostics is redacted once, by the server's backstop, because `/api/diagnostics.json` holds only numbers and fixed words and the dashboard does not redact it. `foreman_budget` returns `why: ''` (not null) when no reason is recorded. Tests: `node --test tests/foreman-reads1.test.mjs` (grouping and span, damaged records, the configuration difference against the real shipped file, GET-only routes, an unchanged state tree and no secret-shaped output, with fixtures built at run time).

## Mismatches and grouped Needs you (`foreman_mismatches`, `foreman_needs_you`, issue #624)
On 5 Nov 2026 the Needs you list had 54 items, most of one cause. Both tools are pure readings of the `/api/view.json` the server already fetches (`foreman-mcp/insights.mjs`): no new route, no new permission, no model call, no lock. Output goes through the same redaction and 24,000 character bound as every tool, and lists are capped at 40 with the true count stated.
- **`foreman_needs_you`**: the Needs you items grouped by the cause part of the item id (`homeowner-pr-538` and `homeowner-pr-540` are cause `homeowner-pr`), most items first: count, the pull requests or issues involved, one example and the action asked (the most common up to three), plus `totalItems` and `distinctCauses`.
- **`foreman_mismatches`**: four kinds, each with the evidence. `implemented-without-pr` (the issue's queue reason says it started earlier with no PR, and no open PR or running job names it); `finished-not-recorded` (a review job's verdict was refused or never recorded, from the Needs you cards); `stale-label` (a closed issue still labelled needs-homeowner, or an open PR with the label, no Needs you item and not awaiting review); `hold-by-old-job` (#583: the card says a stopped job holds the label, but the PR head differs from the held job's head, meaning the head has moved on; a job with no recorded head falls back to: the held job started over 24 hours ago). The hold legitimately stays while the job's worktree is dirty, has unpushed commits or is on another branch, so a head mismatch can be a hold kept for unsaved work. A held job missing from the recent jobs in the view cannot be checked: it is listed in `notChecked` with a `notCheckedNote`. These are heuristics over the view and the remote is not checked: an empty result means none of the four is visible. A job that finished but was never recorded at all cannot be seen from the view and is not claimed.
- Tests: `node --test tests/foreman-insights.test.mjs` (positive and negative cases for each kind, the bound, read-only annotations, and no secret-shaped output with fixtures built at run time). Deploy by copying the `foreman-mcp/` directory as in the install steps; no dashboard change is needed.

## Headline progress numbers (`foreman_headline`, issue #866)

- **`foreman_headline`**: the eight numbers at the top of the dashboard Overview for the last 24 hours and 7 days, each with the previous period: issues opened vs closed (and open now), issues processed (closed out of those open at the start plus opened), pull requests merged per hour, first-pass review approval rate, rounds (reviews, fixes, rebases) per merged pull request, tokens per merged pull request (usage equivalent, not a charge), wasted tokens with the top cause, and rejects (CHANGES verdicts plus blocked jobs). With `card` (and `window`, `limit`) it lists the items behind one number. It reads the same `headline` record the dashboard renders, so the two cannot disagree. The waste record holds 7 days, so the 7-day waste figure has no previous period. The issue list holds every open issue and the newest 200 of any state, so closed counts in a very busy period may be a floor (`issuesPartial`).

## Rebase treadmill measure (`foreman_rebase_stats`, issue #633)
The behaviour half of the issue: a conflict rebase is deferred while another open, non-conflicting pull request is ahead in the review or merge queue (green and unreviewed with an agent able to review it, or holding a PASS that GitHub does not report BLOCKED; a needs-homeowner, decision-held, BLOCKED or unreviewable pull request is not ahead), and starts once nothing is ahead, so the pull request is rebased just before its review or merge rather than on every main move (#633; `rebaseNotNext` in `supervisor/team.mjs`, `tests/rebase-starvation.test.mjs`). A behind-with-PASS rebase is not deferred. A PASS carries across a clean, green rebase whose range-diff shows an identical patch, message and placement, while any difference needs a new review (D-025; `tests/rebase-carry.test.mjs`, `tests/rangediff-placement.test.mjs`, `tests/rebase-safety.test.mjs`). This tool adds the measurement.
- **`foreman_rebase_stats`** (optional `splitAt`, an ISO date or time, and `limit`, default 100, at most 200): for the merged pull requests in the dashboard view, the rebases per pull request, the reviews per pull request (verdicts a review produced; D-025 carried verdicts are not reviews and are reported apart as `carried`) and the time from first recorded activity to merge (mean and median). With `splitAt` the figures are given for merges before and after it, so set it to the day a rebase-policy change was deployed. Open time is measured from the implement time the merge log recorded (issue #717), else from the first job or verdict the view holds (the merge entry itself is not counted), not the GitHub creation time; second-opinion reviews are counted as reviews; only the newest 500 merges are in the merge log, and a pull request with no timestamp is left out of the time figures only.
- Read-only, a pure reading of `/api/view.json`: no new route, no model call, no lock, same redaction and 24,000 character bound. Tests: `node --test tests/foreman-insights.test.mjs` (averages, split, empty and bad input, no secret-shaped output with fixtures built at run time).

## Session reports (`foreman_reports`, issue #612)
Hand-run Tower sessions can leave a final report for the overseer in one fixed folder, so the homeowner no longer carries it by hand. Raw session logs are never exposed: they can hold secrets. With no argument the tool lists the reports (name, time, size), newest first; with a name it returns that one report as text.
- **Folder:** `reportsDir` in the server configuration (and `REPORTS_DIR` in `launcher.env`, which gives the launcher read access to it). Create it owned by root with group `foreman-mcp`, directory mode 750, files mode 640 (group-readable). Only the owner writes. The server never writes there.
- **Names:** one path component, letters, digits, dot, dash and underscore, at most 80 characters, ending `.md` or `.txt`, and not starting with a dot. Anything else, including separators, `..`, absolute paths and encoded forms, is refused. Files that do not match are not listed.
- **Symbolic links** are never followed: they are not listed, and opening one is refused (`O_NOFOLLOW`).
- **Size:** at most 256 KB is read from a file; a result over the output limit (24,000 characters) is cut with a marker `[truncated: N more characters not shown]`. The existing secret redaction is applied to the text, and each call is logged like every other tool.

### Saving a report: `ai-supervisor report-save` (issue #882)
Hand-run sessions do not need to know the folder. An overseer prompt can say "save it with `ai-supervisor report-save 683-rereview.md`" and nothing else about paths (the repository is public, so paths stay out of prompts).
- `ai-supervisor reports-dir` prints the absolute path of the folder `foreman_reports` reads. It exits 3 with a plain reason when no folder is configured, the folder does not exist or is not a directory, or this user cannot write to it.
- `ai-supervisor report-save NAME [FILE|-]` writes the report from FILE, or from standard input for `-` (or no argument), and prints the saved path. It applies the reader's own rules: the name rules above, the 256 KB cap and the secret redaction. Secret-shaped text is refused (exit 3, nothing written, the text is not echoed). The finished marker is added as the last line when missing, so the report reads as `STATUS: finished`. The file is written to a temporary dot file and renamed, so the reader never sees a half-written report; an existing report of the same name is replaced, and a symbolic link at that name is replaced, not followed. Mode 640, group set to the folder's group when the caller may.
- **Configuration (local, never in Git):** `reports_dir` (absolute path, the same folder as `reportsDir` in the server configuration) in `<state root>/team.local.json`, or the environment variable `AI_SUPERVISOR_REPORTS_DIR`, which wins. The folder is root-owned, so run the command as root on Tower.
- Tests: `node --test tests/report-save.test.mjs` (the real CLI against a temporary folder, then the real reader lists and reads the saved report; not configured, not writable, bad names, secret-shaped text, oversize, symlink).

## Host, tests, ticks, item timeline and the report format (issue #636, part 2 of #569)
Added after the 4 and 5 Nov 2026 stalls (load 60 to 80, swap full), where each cause had to be traced by hand. Same rules as every tool: read-only, bounded (24,000 characters), redacted, no model call.
- **`foreman_host`** now also returns `activity`: swap pages in and out per second, disk wait (CPU iowait percent, blocked processes, busy percent per whole disk) and the top 8 processes by resident memory with their swap. Rates are measured over a half-second sample, so the call takes about that long. It reads `/proc/vmstat`, `/proc/stat`, `/proc/diskstats` and each process's `status` file only; the short process name is the only identity shown, and no command line or environment is read. If `activity` cannot be read it is `null` and the original load, memory and swap fields are unaffected.
- **`foreman_tests`**: test-slot use (limit, in use, free), the runs holding a slot, the queue with each wait, and the last 7 days of refused, timed-out, memory-killed and orphaned runs with the reason. Orphaned means processes of a test run survived SIGKILL. The dashboard serves it at `GET /api/tests.json`. Refusals, timeouts and orphans used to appear only on a run's stderr; `ai-supervisor test-slot run` now also appends them (kind, label, reason; capped, one old generation kept) to `<state root>/team/test-events.jsonl`. Runs before that change are not in the record. Memory kills are recorded as `killed`.
- **`foreman_ticks`** (optional `limit`, default 20, at most 100): recent ticks newest first with time, trigger, duration, status, planned actions, GitHub calls, no-op passes and any check result, plus the ticks skipped in the last 24 hours with their reason. The dashboard serves it at `GET /api/ticks.json`. Only the latest tick keeps its error text (the cache holds one); an older error tick shows its status only.
- **`foreman_item_timeline`** (`kind` pr or issue, `number`, optional `limit`, default 60, at most 200): one item across jobs (implement, review, fix, rebase, CI fix) and the reviews and merge (from each pull request's verdicts and merge time, plus the view's activity events), oldest first, with agent, status, duration and cost (usage equivalent). A pull request includes the jobs of the issue it closes. It reads `/api/view.json` only, so jobs outside the recent set and jobs older than the recent job list can be missing; an issue also includes the jobs, reviews and merge of the pull requests that close it; the result says so.
- **Standard report format for `foreman_reports`** (issue #612). A report is a `.md` or `.txt` file whose last non-blank line is exactly `<!-- foreman-report: finished -->`. The writer adds that line last, only when the report is complete. The list shows `finished` per report and a count of `unfinished`; a report read without the marker is headed `STATUS: UNFINISHED` and must not be treated as complete. A marker anywhere but the last line does not count, and the tail of a report larger than the read cap is still checked. Suggested shape: a `# Title` line, a one-paragraph summary, the findings, then the marker.
- Tests: `node --test tests/foreman-reads2.test.mjs` (fake `/proc` trees, the real dashboard handler over a temporary state root, the real CLI refusal path, state tree byte-for-byte unchanged, and no secret-shaped output, with every fixture assembled at run time).

## Install (on Tower, as root; needs the homeowner's approval of D-030)
1. Copy `foreman-mcp/` to a persistent directory owned by root and read-only to the account, outside every Foreman checkout and not on the RAM disk, for example `<install dir>/foreman-mcp`. Record the commit it came from in a `VERSION` file beside it.
2. Write the configuration, owned by root and readable by the account: `{ "viewUrl": "http://<dashboard host>:<port>/api/view.json", "logFile": "<account home>/logs/calls.log", "reportsDir": "<reports folder>", "inboxDir": "<inbox>" }` (`reportsDir` is the folder described in the reports section above; leave it out only if `foreman_reports` is not wanted. `inboxDir` is optional: leave it out unless the inbox below is installed, and see that section for the directory). Use the address the dashboard serves on; it is not kept in Git.
3. Write `launcher.env` beside `launcher.sh`: `NODE_BIN=<absolute node>`, `CONFIG_FILE=<configuration file>`, `LOG_DIR=<account home>/logs`, `REPORTS_DIR=<reports folder>` (the same folder as `reportsDir`; it gives the launcher read access to it), and, only with the inbox, `INBOX_DIR=<inbox>` (the same directory as `inboxDir`; read access to it, write access to `<inbox>/items` only).
4. Create the account `foreman-mcp`: locked password, its own home, no extra groups, and a login shell that can run the forced command (for example `/bin/sh`). Create the log directory owned by the account, mode 0700.
5. Put one line in `<account home>/.ssh/authorized_keys` (home mode 0755 or tighter and owned by root or the account, `.ssh` 0700, file 0600, all owned by the account):
   `restrict,command="<absolute path>/launcher.sh" ssh-ed25519 <public key> <comment>`
   `restrict` turns off the pty, port, agent and X11 forwarding and `~/.ssh/rc`, and the forced command ignores whatever the client asks to run.
6. If sshd uses `AllowUsers` or `AllowGroups`, the account must be listed. Check with `sshd -T` (read-only); do not reload sshd without the homeowner.

### Automatic updates (issue #946)
After the hand install above, Foreman's self-upgrade keeps the copy current. Once, as root, write `/mnt/cache/ai-supervisor/foreman-mcp.install` with one line, `INSTALL_DIR=<the install directory>` (the directory that holds `foreman-mcp/` and `VERSION`). Without that file nothing is installed (`skipped`). If the file exists but the server directory does not, the result is `failed` and alerts. If the server is not in `<INSTALL_DIR>/foreman-mcp` with `VERSION` beside it (Tower: the server is in `srv/`, next to `launcher.sh`, with `VERSION` inside it), add `SERVER_DIR=srv` and `VERSION_FILE=srv/VERSION` lines; only the first line of `VERSION` is the commit, later lines are kept. `launcher.env` keeps its owner, group and mode. A supervisor rollback from the first install after #946 runs the older version's rollback script, which does not restore the MCP copy, so Foreman and the MCP copy can disagree until the next install; the System page flags it.
- Each install of Foreman runs `tools/install-foreman-mcp.sh` from `tools/upgrade-supervisor.sh`, after the supervisor swap. If `foreman-mcp/` in the commit differs from the installed copy, the new copy is checked (identical to the commit, `server.mjs` parses), swapped in with two renames and recorded in `VERSION`; if it already matches, only `VERSION` moves, so it always names the Foreman commit. Code is root-owned, directories 0755, files 0644, `launcher.sh` 0755 (the account only reads it). `launcher.env` is carried over and never replaced.
- The same pre-checks (validator and full tests, before anything is swapped) apply as for every Foreman install. A failed MCP install never undoes the supervisor swap: the previous copy is put back and keeps working, the failure is recorded (`team/mcp-install.json`, an `mcp_install_failed` upgrade record) and alerted once per commit. A supervisor rollback also restores the MCP copy of the version it returns to.
- The System page's Version card and `foreman_status` (`version.mcp`) show the installed MCP commit and flag it when it differs from Foreman's. Nothing is shown while the file above is absent.
- Tests: `node --test tests/mcp-install.test.mjs` (a change under `foreman-mcp/` must be in the upgrade plan).

The server works only while the computer and Claude desktop are running. Nothing is exposed to the internet and no listening port is added.

## Revoke access
Remove the one line from `<account home>/.ssh/authorized_keys`, or lock the account (`usermod -L foreman-mcp`), or delete it (`userdel foreman-mcp`). Remove the server directory and the configuration if the server is retired. On Unraid, also remove the line that recreates the account from `/boot/config/go` and the script it runs.

## The inbox (issue #124, D-031 proposed)
The overseer can propose; only the homeowner can approve. This is the one write the server has, and it goes into one directory.

- **Tools.** `foreman_propose` (kind `prompt` or `issue_draft`, a title, the text, an optional reason), `foreman_proposal_status` (the state and result of one item), read-only `foreman_inbox_items`, and read-only `foreman_inbox` (issue #1197: every card newest first as short id, kind, exact title, state including `submitted` for items Foreman has not picked up, age in minutes, `proposedBy` `overseer` or `system`, and the first prompt line for prompts; optional `state` and `limit`, default 20; refused cards show only when asked for; decision cards carry no time so they list last with no age). The list tool accepts `search`, `kind` and `state`, including kind `decision`; its every-word, case- and punctuation-insensitive matching is the same as the dashboard Inbox, including `1104` or `#1104` for linked work. They appear only when an inbox directory is configured. There is no tool that approves, rejects or runs anything. The dashboard route `/api/inbox.json` is a different, smaller view: status records only (id, kind, title, state, age in minutes, newest first), with no submitted items, no decision cards, no `proposedBy` or first line, and refused cards included; use the tool for the full list.
- **Layout.** `<inbox>/items/<id>.json` is written by the `foreman-mcp` account (the server picks the 32-hex-character name; a call cannot name a path). `<inbox>/status/<id>.json` and `<inbox>/audit.jsonl` are written only by Foreman (root) and readable by the account. The launcher gives Node write permission to `<inbox>/items` only, so the server cannot touch `status/`, the audit log or anything else.
- **What Foreman does with an item** (each tick, so allow up to five minutes before it appears). It reads only regular files of at most 32 KB, validates the shape, refuses unknown kinds and fields, text over 8,000 characters (title 200), control characters, secret-shaped text and AI-attribution text, and allows at most 30 items waiting for approval at once (`inbox.max_pending` in `team.local.json`, 1 to 200; Foreman publishes the value in `<inbox>/status/limits.json`). A refused item records the reason (never the text) in its status. Each valid item becomes one Approve/Reject card in Inbox, showing the exact text. The card is bound to a hash of the file: an item edited after pickup is refused at approval and again at use.
- **Approve and reject.** The card posts to the dashboard's `/inbox` route, protected like the other dashboard writes (D-029): Host, Origin, the secret proof in the state root, and a one-second cooldown. Reject records it and does nothing. Approve is recorded; the next tick acts.
- **An approved prompt** starts one ordinary job (kind `inbox`) in its own worktree and branch `<prefix>inbox-<id8>`, in an implementer slot, under the same allowance, usage-limit, breaker and model rules as an implement job. It never writes as Opus. The prompt text is passed as quoted task data, and the limits (no merge, no approval, no verdict, no review bypass) are stated before and after it. The job writes a short summary to a file Foreman gives it; Foreman redacts it and records it as the item's `result`.
- **An approved issue draft** is posted by the tick as the homeowner's GitHub account, redacted, after a final secret and attribution check. The state `posting` is recorded before the post and a marker comment in the body is looked up first, so it is posted once.
- **Actions (issue #629, D-033 proposed).** `foreman_propose` also accepts kind `action` with a title, `action` (`new_review_attempt` + PR number, `clear_retry_cap` + PR number (clears a retry cap, issue #1086), `reopen` + issue number, `close_job`, `stop_job`, `resume_job` + the 8-character job id from the dashboard) and a `reason` (at most 300 characters). Nothing else is accepted: no command, path or free text target. The card names the action and its target; after the homeowner approves it, the next tick re-checks the target and either does it once or ends the item `failed` with the reason and nothing changed. Refusals: `new_review_attempt` with attempts left, a verdict or a running review; `reopen` as `team reopen`; `close_job` unless the job is blocked, failed or stopped and its PR has a newer head, and unless its worktree was saved (uncommitted work is committed and pushed to `saved/<job>-<branch>`; ignored files are not) and git shows nothing unsaved; `stop_job` of an ended job; `resume_job` of a job on an overtaken head, an agent out of allowance or a full provider role. An agent job cannot approve: approval exists only on the dashboard route.
- **Park, stop and unpark (issue #1115, a decision proposal in the register).** Three more tools, shown with the other inbox tools. `foreman_park` (`number`, `reason`) puts the existing `parked` label on one issue or pull request as Foreman's GitHub App (`github_app` in the host's `team.local.json`, set by approving a host-value item: `app_id`, `installation_id`, an absolute `key_file`; the App needs Issues and Pull requests write; the App's private key stays in an owner-only (mode 600) file on Tower outside Git, refused otherwise, decision proposal D-039, and the installation token is minted per call and never logged). Park does nothing until that setting exists: it is refused with the reason; it never falls back to the owner account. A control item wakes a pass at once, so the result arrives within the tool's wait. A parked pull request stays in the view and the dashboard, and only its actions (rebase, fix, review, merge) are held, and the planner then skips it. `foreman_stop_job` (`id`, the 8-character job id from `foreman_jobs`, and `reason`) runs the supported stop: the stop is recorded on the job before its worker is signalled, the automatic restart is cleared so the job is not started again, and the stop is not an infrastructure fault and uses no attempt (issue #1109). Both write an inbox item of kind `control` that Foreman runs on its next pass without a click, and the tool waits up to 20 seconds for the result. A `control` item has exactly two names (`park`, `stop_job`), is never counted against the pending limit, and cannot release, merge or approve anything. `foreman_unpark` (`number`, `reason`) is the releasing direction: it writes an ordinary `action` item (`unpark`) that the homeowner approves with one click on the dashboard. A reason is required for all three.
- **Results and records.** Parking an already parked item changes nothing and says so; an unknown number or job id is refused with its reason; stopping an ended job reports that it already ended. Parking an item with a running job does not stop the job and the result names it, so the overseer stops it separately. Every control item records who (`overseer`), when, why and the result in its status (read it with `foreman_proposal_status`). The recent records appear as `controls` in `foreman_why_blocked` (for the number parked) and in each row of `foreman_jobs` (for the job stopped).
- **Audit.** `<inbox>/audit.jsonl` has one line per event (time, id, event, kind, SHA-256 of the item). No content and no secrets. A finished item (done, failed, refused, or rejected once its 30-second undo window has passed) has its item file removed at once, so it never counts against the limit; its status record stays for 14 days.
- **Limit and counting (issue #943).** `foreman_propose` counts waiting items the way Foreman does: items Foreman holds as pending plus item files it has not picked up yet; finished items do not count. When that reaches the limit it is refused at submit time with the count, so "submitted" means the item will appear. An item Foreman still refuses after pickup (a failed check, a race) appears in Needs you as one line per reason: "N overseer proposals were refused: reason" (three days).
- **Statuses** (`foreman_proposal_status`): `waiting` (not yet picked up), `pending`, `refused`, `rejected`, `approved`, `running`, `posting`, `done`, `failed`.

### Install the inbox (on Tower, as root; needs the homeowner's approval of D-031)
1. Create the inbox directory outside the Foreman state root and outside every checkout, owned by root and readable by the account: `<inbox>` mode 0755, `<inbox>/status` root-owned 0755, `<inbox>/items` owned by `foreman-mcp` mode 0700. Foreman (root) reads and writes everywhere in it.
2. Add `"inboxDir": "<inbox>"` to the server configuration file, and `INBOX_DIR=<inbox>` to `launcher.env`. Copy the updated `foreman-mcp/` directory (including `inbox.mjs`) and record the commit in `VERSION`.
3. Add `"inbox": { "dir": "<inbox>" }` to `team.local.json`. Without it Foreman ignores the inbox and the dashboard has no `/inbox` route. Restart the dashboard server so it reads the setting.
4. Check as the account (`ssh foreman-mcp@<tower>` through the forced command): `tools/list` shows the two new tools; a proposal appears in `items/`.

### Trial account and revoking access
The trial account's key and forced command are unchanged by this feature. To stop proposals but keep reads: remove `INBOX_DIR` from `launcher.env` and `inboxDir` from the configuration (the tools disappear), or remove the `inbox` block from `team.local.json` (Foreman stops reading the inbox and the route disappears). To revoke everything: remove the one `authorized_keys` line, lock or delete the account, as above. Items already approved but not yet started stop being planned when the `inbox` block is removed.

## foreman_issues (issue #951)
Read-only search of every issue and pull request, open, closed and merged, served from Foreman's own index (`<state root>/dashboard/issue-index.json`) through `GET /api/issues.json`, with no GitHub call per request. It lets the overseer, who cannot reach the GitHub API from Claude chat, check whether an issue already exists before drafting one.
- Filters: `text` (every word in the title or body), `kind`, `state` (open, closed, merged, all), `label`, `number`, `from`/`to`, `author`, `updatedSince`; for pull requests also `head`, `ci`, `verdict` (from Foreman's recorded verdicts for the current head) and `issue` (a linked issue). Unknown arguments and bad values are refused.
- Results: number, title, state, labels, updated, URL and a redacted excerpt. A `number` lookup returns the full redacted body (12000 characters at most) and the latest 5 comments. `coverage` says whether the history is complete.
- Refresh: at the end of each real tick, one bounded `gh ... list --search "updated:>=<cursor> sort:updated-asc"` call per kind (100 items). A new index pages back through the history one page per tick; once caught up a tick fetches only what changed, and a pass GitHub proved unchanged makes no call. The refresh is best effort and never fails a tick. Text is redacted before it is stored.

## Sent alerts (`foreman_alerts`, issue #949)
Every alert is appended to `<state root>/team/alerts.jsonl` with its delivery result. The MCP account cannot read the state root, so one more GET route on the dashboard the server already reads, `/api/alerts.json` (`supervisor/alertsview.mjs`; same host check, GET only, no write, no new port, no new permission), serves a bounded, redacted view. Until the dashboard is restarted on the new version the tool answers HTTP 404.
- **`foreman_alerts`** (optional `since` ISO date or time, default the last 24 hours; `contains`, case-insensitive text; `delivered`, true or false; `limit`, 1 to 200, default 50): `alerts` newest first with time, redacted text and whether it was delivered; `groups`, alerts grouped by their normalised text (lower case, with URLs, quoted names, paths and branch names, commit SHAs and numbers replaced), most frequent first (at most 50; `groupCount` is the total and `groupsTruncated` says some were left out), with count, delivered and not delivered, first and last time and one example; `perDay`, totals for the last 7 UTC calendar days (today and the 6 before; the text and delivered filters apply, `since` does not).
- Only the last 4 MiB of the log is read (a note says when the oldest alerts may be missing). Read-only, redacted twice (dashboard, then server), no model call, no lock. Tests: `node --test tests/foreman-alerts.test.mjs`.

## Writing issues (issue #1177)

When the overseer writes or edits an issue, use [`work-item-template.md`](work-item-template.md): a "Wanted (before the PR)" list and a separate "After install (checked on Tower)" list with who checks each item. ## Homeowner stop record (`foreman_stop_record`, issue #1161)
- Takes no arguments. Reads the reason of the upgrade latch (`/api/installs.json`) and any Needs you item about a pause, latch or stop, finds the `.md` or `.txt` file paths those reasons name, and returns for each: `path`, `modified`, `bytes`, `text` (redacted with the usual MCP redaction, then cut at 10,000 characters; `truncated` says so).
- **Not a file reader.** Only a path a current reason names, only directly inside an allowed directory, only a regular file reached without a symbolic link. Anything else comes back as `refused` with the reason. Allowed directories: `stopDirs` (a list) in the server configuration file (or `FOREMAN_MCP_STOP_DIRS`, colon separated); default `/mnt/cache/logs/agent-cleanup`.
- A homeowner stop is a hold whose reason names a stop record. With none it answers `{ "stop": false }`; an automatic hold (a rolled-back upgrade latch, the routine `paused-new-work` open-PR cap item, any reason naming no record file) is listed under `automaticHolds` and is not called a homeowner stop.
- `launcher.env` may set `STOP_DIR` (the same single directory as `stopDirs`; default the path above). The launcher gives the server read access to it.
