# Team loop (issue #23)

Status: implemented and running on Tower (see `docs/ai/CURRENT_HANDOVER.md` for the installed version). Decisions: **D-019** (bounded automatic restart) and **D-020** (supervised jobs run with the interactive agents' access), both homeowner-approved.

## What it does
`ai-supervisor team tick` is a dispatcher that **makes no model call**. It uses GitHub API calls (`gh`, argument arrays, no shell) and local files only. The existing five-minute reconcile cron already runs `reconcile`, which now runs one tick when `supervisor/team.json` has `"enabled": true` (shipped as `false`; enabling is an explicit act). Only one tick runs at a time (lock with PID and start time). A tick:

1. **Ingests verdicts** from finished review jobs and posts them as a PR comment with a machine marker.
2. **Notifies** for blocked or failed jobs: label `needs-homeowner` plus one comment saying what is needed. Other agents keep working.
3. **Allowance modes** (issue #56, [allowance-scheduling.md](allowance-scheduling.md)): each agent is `normal`, `reviews_only` or `waiting` from its provider-reported weekly burn; a mode change is recorded and alerted once. A `reviews_only` agent starts only reviews and fixes on its own PRs, a `waiting` one nothing; their unstarted issues may be implemented by an agent with headroom ("reassigned for allowance").
4. **Plans at most one merge**, then **dispatches** per role slot (issue #148): `limits.roles` is `{ implementer: 1, reviewer: 1 }` plus an optional `rebaser` (default 1) (any positive count per role, no fixed ceiling, issue #344) and an optional `overall` that defaults to the sum of the role counts (3 for 1+1+1), counting manual jobs. The implementer slot runs implement, continue, fix and ci-fix jobs; the reviewer slot runs review jobs; the rebaser slot runs rebase jobs (issue #460), so a rebase never holds the implementer slot from new work, while rebases still plan first (the rebaser slot is filled before the others and `rebase` leads the per-agent order). A rebase that ends incomplete records why on the job (`incomplete`: cause, detail, attempts; cause is `conflict`, `postcondition_not_met` with the detail, or the run event such as `crash`), reported as `incompleteRebases` on the tick. Any agent with allowance can fill a free slot, and one agent can fill both at once, each job with its own role's model entry. When several agents could fill a slot, a review goes to an agent on another provider than the PR author before one on the author's provider, and both before a second-opinion review, and an implement job to the issue's owner before an agent taking it over. For each agent the first rule that applies is chosen (a job the dispatcher has no record of counts against the implementer slot). `limits.per_agent` is deprecated: it is accepted for one release, mapped to both slots, and reported as a warning on every tick. `team status` and the dashboard show the slots ("Implementer: claude · sonnet · PR #146 · #104 …", "Reviewer: idle"):
   1. *Rebase* this agent's own open, non-draft PR in two cases only (issue #79): it conflicts with its base, or it already has a PASS and green CI but GitHub reports it `BEHIND` its base (a rebase right before merge). Main moving is never a reason, and red CI on the merged result goes to the CI-fix job. Max `max_fix_attempts` per head. GitHub runs no `pull_request` CI on a conflicting PR, so this comes first. The job is a conflict-only rebase that keeps commits unamended, pushed with `--force-with-lease`, with a `git range-diff` comment. Post-condition: a new head that GitHub reports mergeable (it is asked up to four times, because mergeability is computed lazily). When the job completes, the dispatcher compares the old and new head itself (`supervisor/rangediff.mjs`: no merge commit in either range, the same net change against the base, and every commit has the same patch and message, compared as exact text including whitespace and context lines, not by patch-id; only blob hashes and hunk line numbers are ignored, as `git range-diff` shows `=`; each hunk must also sit where upstream changes alone would move it, so a hunk placed in a different repeated block does not carry, and a diff header that cannot be parsed, such as a git-quoted file name, fails closed; a refused carry only means the new head is re-reviewed; issue #128). If equal, a recorded PASS carries to the new head with a public `Verdict carried` comment, and the usual gates (green checks, mergeable) still apply. Otherwise, or if the comparison fails, nothing carries and an independent reviewer (a fresh session on a different model, D-024) reviews the new head. Only a PASS carries. **No silent commit loss (issue #158):** the job fetches right before rebasing and starts from the remote head (`ai-supervisor rebase-prepare`), never a cached local branch. Its push (`ai-supervisor rebase-push`) first checks by patch-id that every commit of the old remote head not on the base is in the result, refuses and pushes nothing if one is missing, and pushes with `--force-with-lease` against the fetched head (a moved branch pushes nothing). After the job the dispatcher repeats the check, stores old head, new head and the commit list on the job record (shown in Activity), and for a lost commit comments the ids and subjects, labels the PR `needs-homeowner` (a Needs you item) and carries no verdict. A later review that repeats a finding fixed earlier flags it as "possibly lost in rebase". **A refused push is not retried (issue #1193):** when `rebase-push` refuses (a lost commit or change), it leaves a note in the worktree's git directory; the job's post-condition then reads "the guarded push was refused", the job is not run a second time, the head's rebase attempts are spent so the planner stops, and the PR gets one `needs-homeowner` notice quoting the guard. **An agent that cannot finish is not retried either (issue #1207):** the prompt tells it to run `ai-supervisor rebase-stop --worktree DIR --old OLD_HEAD --reason TEXT` before it stops (conflicts that are not mechanical, a check or tool it may not use); that leaves the same note, so the same hold and one `needs-homeowner` notice follow, with the agent's reason quoted. A new head restarts the lane.
   The guarded push (`rebase-push`, issue #1228) compares what each commit changes, not whether lines of the old branch still exist. Commits are paired by patch-id, then by author, date and subject; for a pair whose patch differs, every hunk of the old commit must be found again in the new commit, or in a new commit no old commit pairs with (a restore the agent made in a commit of its own), at any position and with any context, or be a change main already made between the merge base and the base tip (read from `git diff`, not guessed), or a line a longer added line contains whole (both sides edited one line and the resolution joined them), or, in a hunk that also removed a line, a line whose newly introduced tokens all sit on one other added line (a list or call both sides edited and united, issues #580 and #640; a pure addition is never matched this way), or `export { X };` for a name main already exports by its declaration (PR 1131), or a renumbering (the line differs from a line of the new commit only in a number that main's own added lines use, as when `D-040` became `D-042` after main took `D-040`). A refusal names the commit, the file and the hunk and says whether the change is `missing` or `altered`. The first refusal is repaired in the same run: the agent restores the named change, runs the checks and calls `rebase-push` once more. A second refusal, or the agent stating that main removed the change on purpose, ends the run with `rebase-stop`. The agent never amends or rewrites commits, and a failure caused by the PR's own growth (size ratchet, tests) ends with `rebase-stop` at once. The decision register is not special cased. Implementation: `supervisor/rebasehunks.mjs`.
   2. *CI fix* this agent's own open, non-draft PR with a completed failing check on its current head (shares the per-PR `max_fix_attempts` budget with CHANGES fixes). The prompt names the failing checks (only names that pass a strict character check). Post-condition: a new pushed head.
   3. *Fix* this agent's own PR that has a CHANGES verdict on its current head. `max_fix_attempts` (default 2) is counted per PR across heads; when it is reached while the PR is still rejected, the dispatcher posts one `needs-homeowner` notice and starts no further fix jobs for that PR.
   4. *Review* an open PR with all checks green, no merge conflict and no verdict yet for that exact head (max 2 attempts per head), when this agent's review model is not a model that wrote the head (see *Review independence*). A one-agent roster reviews its own PRs this way.
   5. *Implement* the next owned open issue whose prerequisites (parsed from the issue's `Prerequisites:` line, numbers only) are closed, with no open PR or job already on it and no `needs-homeowner` label. Branch `<agent>/issue-<n>-<slug>`, worktree `DevTest-Infrastructure-<agent>-<n>` (D-018).

`team tick --dry-run` prints the planned actions and writes nothing.

## Trust
- A review job writes `verdict.json` into its own inbox directory (`<state>/team/inbox/<ticket>/`) using `contracts/verdict.v1.schema.json`: `{pr, headSha, verdict: PASS|CHANGES, findings: [{kind: blocking|follow-up, text, scope?: code|tests|description}], commandsRun[]}`. Blocking means correctness, security, data loss, scope violation, new architectural deterioration in the changed code (docs/coding-standards.md; pre-existing debt the change did not worsen is a follow-up) or a failed acceptance criterion. CHANGES requires a blocking finding; PASS has no blocking findings and may have follow-ups. PASS follow-ups are batched per area, not one issue per review round (issue #864); issue #1061 may change how follow-ups are handled, so this paragraph links to it rather than repeating the rules. Fix-round re-reviews check the previous blocking findings and regressions caused by the fixes; new non-blocking observations become follow-ups.
- The dispatcher records a verdict only from a **finished** job it created, for the job's own PR and head. **Comment text is never read**, so a comment on the shared account cannot approve anything. A review counts only if it is independent (next bullet); one that is not is refused at planning and again when the job finishes.
- **Review independence (issue #152, amends D-021).** A review is a full review when it is a fresh session in the reviewer's own review worktree, the reviewer runs the tests itself, and the reviewer's model differs from every model that wrote the PR head. The writer models come from the dispatcher's own job records for the PR (implement, continue, fix, ci-fix and rebase jobs: provider and `model`); a PR with no records counts as written by its branch author's provider on an unknown model. A different provider is always independent. On the same provider both models must be known and different; an unconfigured model is unknown, so such a review is refused (planning schedules nothing, `team status` shows "review refused: … the model that wrote it", and a finished job on a writer model records no verdict). The same provider on another model is a full review: its PASS is merge-eligible and no post-merge review is queued. Provider-agnostic (D-012). A roster of one agent is valid (e.g. implement on `sonnet`, review on `opus`). "Out of allowance" (`supervisor/interim.mjs`) is still evidence only and still holds a review for a reviewer at its limit; the weekly threshold is `out_of_allowance.weekly_at` (shipped 0.995, the same value as `budget.exhausted_at`, so a `reviews_only` agent may review until its allowance is used up; the retired `interim_review.weekly_at` is read as a fallback with a deprecation warning). The old `post-merge-review` queue is gone: entries queued earlier are dropped on the next tick unless the merged PR touched a second-opinion path. D-024 is homeowner-approved and supersedes D-021 (no interim review and no post-merge review queue).
- **Second opinion (optional).** `second_opinion: { "paths": ["supervisor/upgrade.mjs", "network/**"], "reviewer": "<agent>" }` in `team.json`. A PR that already has a PASS and touches one of those globs (`**` crosses directories) gets one extra review from the named agent when its provider differs from every provider that wrote the head and it has allowance; merge waits for it while it can run. A reviewer that is out of allowance, or out of attempts, does not hold the merge. CHANGES from the extra review rejects the head like any CHANGES; a PASS leaves the primary PASS in place. An unreadable file list fails closed (merge held, extra review planned). Not configured: no extra review, ever.
- Prompts contain validated tokens (numbers, SHAs, branch names, ticket). A fix-round `review-scope.json` contains the previous reviewer's validated, length-bounded blocking finding text as task data; it is not an instruction or an approval signal. Issue and PR text never enters a prompt or a scope. A rebase after either verdict receives a full review unless its commits are all unchanged (a PASS then carries, see rule 1). A review is not scheduled for a reviewer that is at its usage limit or in `waiting` mode: the hold and its reason show in `team status` and on the dashboard.

## Merging
The dispatcher merges, not an agent, and only when **all** hold: a recorded PASS from an independent reviewer for the **exact** current head, every check on that head completed green, the PR is mergeable and not a draft, and the branch belongs to a configured agent. The merge passes `--match-head-commit`, so GitHub refuses it if the head moved after the verdict. PRs that target another agent's branch (e.g. a fix PR) follow the same rule. After a merge the dispatcher comments on the linked issue and moves the board card (`done` for merges into `main`, otherwise `in review`). Issue closure stays with GitHub `Closes #n` keywords. **Merged is not deployed and not verified working.**

## Completion is a post-condition, not an exit code
review → a valid verdict recorded; fix → a new head pushed; implement → a PR open from the branch. Exit 0 without it is `incomplete`: retried once with a fresh launch, then `blocked` (`needs-homeowner`). A checker that throws counts as not met and logs only the error class.

## D-019 restart
`autoRestart: true` (set by the dispatcher) restarts a job that stopped on a usage limit **fresh** from issue, Git and handover state. A provider session id is passed only when that provider's `resume` capability is `supported` (today neither is). Wait = reported reset + 2 minutes; if no reset was reported, parsed in the future and provider-reported: 1 h, then 2 h, then 4 h, then `blocked` (three restarts at most). No provider call happens while waiting. No paid fallback; overage use blocks for a human (see #21). It is allowed when the provider supports `launch` and `non_interactive`; the older `autoResume` (session resume) still requires every capability verified. **The reset parser stays `unverified` until the first real limit hit per provider is captured as a fixture.**

## D-020 access
Interactive launcher (`/root/bin/ai-agent`): Codex `--dangerously-bypass-approvals-and-sandbox`, Claude `--permission-mode auto`. Provider manifests carry `access.standard` and `access.full` argument lists; adapters append them (no provider branch in core). A job gets full access only when its spec says `access: "full"`, only for roles listed in `supervisor/access.json` (`devtest`), and the dispatcher refuses to launch anything unless `D-020` is `homeowner-approved` in the register merged on `origin/main`. Other roles and jobs without the field run `standard`. D-007, D-009, D-010, no reboot, no production Home Assistant change and no secret disclosure still bind (stated in every full-access prompt).

## Local configuration and upgrades (issue #30)
`supervisor/team.json` is the reviewed, versioned file (shipped `enabled: false`). **Never edit the installed copy** under `/mnt/cache/ai-supervisor/versions/<sha>/`: the next upgrade replaces it, and the payload would no longer match the reviewed commit. Local settings go in **`/mnt/cache/ai-supervisor/team.local.json`** (state root, outside `versions/`, mode 0600). Upgrades never read, write or replace it. The code that validates both files and loads them (`validateTeamConfig`, `applyLocalOverride`, `loadTeamConfig`) is `supervisor/teamconfig.mjs` (issue #1239); `supervisor/team.mjs` re-exports it. Example:
```json
{ "enabled": true, "limits": { "overall": 2 }, "agents": { "claude": { "issues": [5, 6] } } }
```
Only `enabled`, `limits`, `depends_on_overrides`, `alerts`, `models`, `budget` and each agent's `issues` can be overridden; repository, paths, providers, access mode and board always come from Git. An unknown key, a bad type or an unparsable file makes the tick fail closed with an error naming the file (never its contents).

**Delivered work.** Before planning an implement job the dispatcher lists merged PRs. An issue is skipped when it is closed, or a merged PR from a configured agent branch `<agent>/issue-<n>-…` or a merged PR whose closing reference names it exists. Issue #23 stays open until verified working; it is kept out by its `tracking` label (below).

**Dependency gating for every lane (issue #1103).** The [dependency declaration format](ai/dependency-format.md) is the only body syntax Foreman reads; a malformed declaration holds the issue and raises one Needs you item rather than being guessed. A prerequisite is **met only when installed**: its issue is closed as completed, its pull request is merged, and that merge commit is in the installed version (the version the `current` link points at, or an ancestor of it). Each prerequisite has one state: `open`, `merged_not_installed`, `installed`, `closed_not_planned` (closed as not planned or a duplicate; one Needs you item asks for the line to be repointed) or `unknown` (a failed or missing lookup, or no merge commit to compare; never treated as met). A number may name an issue or a pull request. Every referenced issue is looked up by number with no cap on how many (a closed result is kept in the state file, so the next pass does not ask again; an open one is asked again each pass, and the stop step hands its lists to the planner so one pass reads them once); a closed prerequisite older than the cached merged list is resolved through the pull requests that closed it, read by number. A dependency cycle holds every member and raises one Needs you item naming the loop. Every lane honours the gate: implement (the exclusion in the queue), and review, fix, cifix, rebase, continue and merge of a pull request whose branch names an issue (`gateReason`, shown as a skipped lane with the reason). The check runs at the start of each planning pass against the installed version read at that moment, so the pass after an install already sees the prerequisite as met. If a running job's issue gains an unmet prerequisite, the next tick stops the job cleanly (`dependency-stop`), marks it so no attempt, failure or breaker waste is counted, and the issue waits and is queued again once the prerequisites are installed; an `unknown` state (a failed lookup) stops a running job the same way, because unknown is never met. Each waiting issue records since when it waits (`depWait` in the team state) and the reason per prerequisite. `foreman_why_blocked` returns `dependencies` with `dependsOn`, `blockedBy` and `unlocks`; `foreman_plan` lists `skippedForDependencies`; the queue and Work rows say `waiting for #N still open; ...`. The older forms (`Prerequisites:`, `Follow-up to PR`, prose dependencies, `depends_on_overrides`) no longer hold an issue in the planner or the queue; the only other hold is a `waiting_on` list a stopped job reported itself. The dispatcher's own split follow-up issues carry a declaration that follows the format. The pure rules are in `foreman-mcp/dependency-parser.mjs`; the planner wiring is `supervisor/teamdeps.mjs`.

**Which issues are eligible (issue #212).** Every open issue is eligible by default; a new issue enters the queue on the next tick with no config edit. An issue is excluded when it is labelled `epic`, `tracking`, `parked` or `needs-homeowner`; when its `Depends on:` line names a prerequisite that is not yet installed or is malformed (see the next paragraph; that line is the only dependency source read from an issue body, and `Prerequisites:`, `Follow-up to PR #N`, prose such as `after PR N`, and `depends_on_overrides` no longer hold an issue); or when it is delivered or already has a PR. An implement job that stops with no pull request because a prerequisite is still open (it writes `waiting_on` numbers to its `waiting-on.json`, only; the issue body is no longer read for it) ends with status `waiting_on`, not `blocked` or `incomplete`: it is not counted as a failure, the issue is not marked implemented and not labelled `needs-homeowner`, and it is queued again when those items merge. Such a stop is never labelled `context_too_large`. A `Depends on:` line that names a pull request closed without merging raises a Needs-you item to repoint it; a `waiting_on` hold from a stopped job is released when the item leaves the open list, with no card. A prerequisite closed as completed with no linked pull request cannot be proven installed: it holds the issue (and stops a running job) and raises a Needs-you item. The `agents.<name>.issues` lists only set order and assignment: listed issues go to their owner first, then any agent with a free slot takes the unlisted ones in number order. The shipped lists are empty; ordering comes from the ranking and the queue rules above, and a list in `team.local.json` is a local override only. The dashboard Work page lists every excluded issue with its reason; excluded issues are not counted as "in no queue". Deploy precondition: create the `epic`, `tracking`, `parked` and `needs-homeowner` labels and label the epic, tracking and homeowner-gated issues (#37, #98, #159, #8-#14 and similar) before relying on the automatic queue; an unlabelled issue is eligible. A referenced PR that is outside the recent merged list is looked up by state, and only a PR GitHub reports CLOSED is treated as closed without merging.

**Upgrade procedure** (after Codex PASS and the dispatcher merge; Claude/Codex never run it unattended):
1. From a clean checkout of the merged commit on Tower: `node tools/validate-project.mjs && node --test "tests/**/*.test.mjs"`.
2. `ls -l /mnt/cache/ai-supervisor/team.local.json`; if missing, create it with `{"enabled": true}` (mode 0600) to keep the loop on.
3. `bash tools/upgrade-supervisor.sh` (it refuses a payload containing `team.local.json`, copies `supervisor/`, then runs `diff -r` source vs. installed and aborts on any difference).
4. Verify: `diff -r supervisor /mnt/cache/ai-supervisor/current/supervisor` is empty (the override is not in the payload, so nothing needs excluding), `team.local.json` is unchanged, `ai-agent --supervisor team tick --dry-run` plans no job for #2 or #23.
5. Rollback: re-point `current` to the previous `versions/<sha>` and restore the wrapper backup the script prints; the override is untouched.
The temporary hand edit of the previous payload (`versions/8f2e386…/supervisor/team.json`) is superseded by this change; the old `current` version stays as rollback.

## Tick resilience (issue #35)
A failure of one item (a lease conflict, one `gh` error, a failed comment) is recorded in the tick report under `skipped` with a reason, and the tick continues with the other agents and items; attempt counters and the "implemented" mark are only set after the job was created. Verdict and needs-homeowner comments are recorded in state and saved before they are posted (and un-recorded if the post fails), so each is posted once per job and head, or once per job and state, however many later ticks fail. The dispatcher releases the leases of its own jobs that reach `completed` or `stopped`, including ones resumed by hand; `blocked` and `failed` jobs keep their lease until the homeowner decides.

## Checkouts that are not linked worktrees (issue #57)
A job's worktree must be a linked worktree of the configured repository. The check resolves the git directory from the worktree's own absolute path (`git -C <worktree> rev-parse --git-common-dir`, resolved against that directory), never from the process working directory, so it behaves the same under cron, from `/`, or from a directory with no `.git`. A standalone clone (for example an agent's own `git clone` at the path the dispatcher would use) is not accepted. This is a condition for the homeowner, not a failed tick: the action is reported under `blocked` (not `skipped`), a "Needs the homeowner" notice is posted once on the PR, the action is not planned again for an hour, and the other agents and items carry on. Fix it by moving the work to a linked worktree (`git worktree add`) or removing the checkout.

## Config migrations on install (issue #153)

A release that replaces a `team.local.json` key ships a numbered migration, `supervisor/migrations/NNN-name.mjs`, exporting a one-line `description` and a pure `migrate(oldLocalConfig) -> newLocalConfig`. It is reviewed like any code; there are no shell hooks. Before a live tick, `runMigrations` runs every migration above the applied number, in order: it writes a mode-600 backup (`team.local.json.bak-<timestamp>-NNN` beside the file), applies the function, validates the result against the shipped config, writes it atomically, records the applied number in `<state root>/team/migrations.json` and appends a line to `<state root>/team/incidents.jsonl`. The dashboard Activity shows each one. A reinstall keeps the state root, so an applied migration never runs again. Without a `team.local.json` the migrations are recorded as applied and nothing is written.

A failing migration (exception, invalid result, unreadable file) leaves `team.local.json` untouched, skips that tick, records the failure once and raises a **Needs you** item naming the migration. The next tick retries it, so fixing the file by hand clears the item. A dry run (`team status`, `team tick --dry-run`) runs no migration.

Migrations run under the tick lock, so a cron tick and a manual `team tick` cannot run the same one twice. A recorded failure is cleared when its migration is no longer shipped (a hotfix dropped it, or a rollback went to a version with fewer migrations). On the normal self-upgrade path a failing migration makes the first live tick of the new version fail, so the upgrader rolls back and the previous version keeps ticking; the Needs you item then reads as a skipped tick, not a stopped loop. Decision: a rollback does not undo migrations already applied. The migrated `team.local.json` and the applied number stay, and the backup beside the file is the way back. Migration error text is redacted in Activity as it is in Needs you.

Shipped: `001-drop-per-agent` removes `limits.per_agent` when `limits.roles` is not set locally, so the shipped roles apply.

## Foreman unblocks itself (issue #163)
Foreman clears a known, bounded, reversible cause itself and raises Needs you only for a real decision.

- **CI.** A check whose latest run on the head was cancelled or timed out, with no later run, is re-run once per head after `limits.cancelled_wait_ms`. If the rerun fails, `cifix` starts as usual; a timeout after the rerun counts as a failure. A rerun that is cancelled again leads to Needs you (#149). Superseded cancellations are green.
- **Secret scanners (#400).** A `cifix` round whose only failing checks are secret scanners (GitGuardian and similar) is not counted toward `max_fix_attempts` and never escalates, because the fix job cannot clear a flagged old commit. Normally one such round runs per PR; if the flag or notice cannot be posted the round repeats, at most 3 times. Once the homeowner item exists (`scanOnlyAnnounced`), later heads wait for the homeowner to resolve the incident. When the scanner check on a later head is green, the markers are cleared, so a new flagged secret raises a new item. A round with any other failing check counts as usual.
- **Transient job stops** (`crash`, `network_error`, `incomplete`, `transient_rate_limit`): the job is resumed once after `limits.unblock.cooldown_ms`, without a notice. An agent out of allowance waits. If it stops again, the usual Needs you notice follows. `usage_limit` and `retry_exhausted` are never resumed automatically (D-019 bounds those launches; the homeowner decides), nor are auth errors and a stale handover. Only a stop nobody was told about is resumed: a job already reported to the homeowner, a PR that is no longer open or whose head moved, and an issue that is no longer open are recorded in `state.unblock.noResume` and handled as before. At the budget limit the limit item is raised and the job notice follows.
- **Deviation from issue #163 item 2.** The issue lists "usage limit" as a transient stop to resume once. This is deliberately not done: D-019 already bounds restarts after allowance limits, and `jobs.resume` would reset the attempt counters, so `usage_limit` and `retry_exhausted` stay with the homeowner. Read the acceptance check against #163 with this in mind.
- **Fix limit.** At `max_fix_attempts` one final round runs per PR (fix or CI fix) as a fresh session on the same configured model, with `review-history.json` (every verdict and finding) as task data. Then a fresh review runs as usual. The job may write `split.json`; the dispatcher accepts a proposed split only for a follow-up finding (a finding reported as blocking in any review is never split automatically; that needs the homeowner) that appears in a review of this PR and does not overlap (five consecutive words, or a whole line) the issue body or an `OWNER` comment on the issue. Accepted findings become one follow-up issue queued at the end of the author's list (`state.unblock.queued`, never `team.local.json`); the re-review is told they are out of scope. Anything unverifiable is refused. Only if the final round is rejected does the fix-limit Needs you notice appear. If the unblock budget is spent before the final round could run, the limit item is raised and the fix-limit notice says that no final round ran. It never moves to a stronger model, and the Needs you item offers no paid option: it lists what was tried (each round a fresh session with the findings, the final round with the option to split out-of-scope findings) and the same choices on every path (the card, the PR notice and the AI-channel alert use one list, whether or not a final round ran or a write block applies): wait for another agent to be able to review, split the PR, change the approach, or fix it by hand. Raising `max_fix_attempts` is mentioned only as allowing more rounds on the same model. When a write block (a job that would remove the last independent reviewer, or a review model assigned writing) is why no further round can run, the card also states that reason.
- **Stale labels.** A `needs-homeowner` label that Foreman added is recorded with its cause (job blocked, fix limit, cancelled CI) and removed, with a comment, when the cause clears: the job runs or completes, a new head is reviewed with PASS and is not red (an unreviewed or pending head does not count; clearing re-arms the fix-limit notice, so a later rejection is raised again), the check is green. Labels Foreman did not add are never touched.
- **Budget.** Every unblock (rerun, resume, escalation, label removal) counts against `limits.unblock.per_pr` and `per_day` (defaults 4 and 12, UTC day). At the limit Foreman stops and raises one Needs you item per limit that names it.
- **Visibility.** Each unblock is `Foreman unblocked: <what>, <why>, <result>` in Activity (`state.unblock.log`) and in the tick report (`unblocked`).
- **Never automated:** merging without an APPROVED verdict on the exact head, persistent changes to `team.local.json` limits, dismissing a secret-scanner finding, dropping homeowner-required scope, overage or paid credit, force-pushing to main. None of the code above calls `merge`.

## An issue too large for one session (issue #244)
When an `implement` job reports `context_limit`, every restart with the same scope would fail the same way (job 6c72e71d spent four sessions, about 3.7M input tokens, and produced nothing). So the supervisor core does not restart it: the job ends `blocked` with `context_too_large`. Other job kinds still get one fresh session.

The team loop then, once per issue:
1. Starts one cheap read-only `split` job (model entry `split`, falling back to the agent's `review` entry; allowed action `read` only). It writes `split-draft.json` to its inbox: 2 to 8 children, each a one-line title and scope. The file is shape-checked, length-bounded and redacted before use.
2. Posts the proposal on the issue and labels it `needs-homeowner`. The dashboard shows one **Needs you** card with the spend of the failed attempt and the action. A draft that is missing or invalid raises no split item; the split job's own blocked state is reported the usual way.
3. **Accept split**: `ai-agent --supervisor team accept-split <issue>` files each child as an issue (a marker makes a repeat or a crash half way safe), queues them for the same agent and comments on the parent. Foreman removes the label it added. The parent is never started again; close it when the children are done.

**Reopen an issue (issue #490).** Foreman never plans a second implement job for an issue it already started, even after the pull request was closed unmerged. After re-scoping the issue, `ai-agent --supervisor team reopen <issue>` clears that mark. It takes the tick lock and refuses unless the issue is open and has no open pull request and no running or unfinished job for it, and no leftover worktree `DevTest-Infrastructure-<agent>-<issue>` or local branch `<prefix>issue-<issue>-*` (the next implement job would reuse them as they are, rejected commits included; remove them first with `git worktree remove` and `git branch -D`). Pull-request jobs (review, fix, rebase, cifix) are matched by their branch. It writes an entry to the unblock log (shown on the Activity page) and changes no other issue. It is never run automatically.

The Usage page has a **Failed attempts** card (`view.failedSpend`): jobs that ended failed or blocked with their tokens and CLI cost estimate. Unknown stays unknown, not zero.

## Open PR cap (issue #250)
`limits.max_open_prs` (shipped default 8, overridable in `team.local.json`; unset means no cap) caps the open unmerged PRs of the configured agents, drafts included. At or above it no implement job starts (own or reassigned), and the implementer slot takes rebase, CI fix, fix, continue or review work instead; reviews keep the model-independence rule of D-024. The dashboard shows "Paused new work: N open PRs (cap M)" while paused and drops it once the count is below the cap.

**The cap cannot deadlock (issue #320).** A PR that cannot move until something outside the cap happens is not counted: it is labelled needs-homeowner, its PASS is held on a homeowner decision (D-024), or its issue has an open prerequisite that has no PR yet (only a new implement job, which the cap would block, can unblock it). The pause line then adds "N more waiting on you or an unstarted issue are not counted". Review gates are unchanged. If the cap still blocks and none of the counted PRs can progress (each is stuck on the fix limit, an unmergeable state, or has no independent reviewer, and none is a draft that could be continued), one Needs you item (`cap-deadlock`) names the PRs and the choices: merge or close one, resolve what they wait on, or raise `limits.max_open_prs`. It clears on the next tick once a PR can move or the count falls below the cap. `limits.max_open_prs` is not the same setting as `change_check.max_open_prs` (the number of PR heads the change check will page, see below).

**Description rounds (issue #1226).** The reviewer gives each finding in `verdict.json` an optional `scope`: `code`, `tests` or `description` (the pull request text, not the diff). A finding without a scope counts as `code`. When every blocking finding on the head's CHANGES verdict has scope `description`, the planner returns the fix action with `description: true`: a short job (job kind `fix`, flag `description` on its record) that edits the pull request body only. It is not given `edit` or `push_feature_branch`, and its post-condition `description_edited` requires the same head, a changed body and a body that still passes the requirements table and cite gate (a pushed commit fails it). It is counted in `descRounds` per PR, not in `fixAttempts`: at most 2 description rounds per PR in addition to the fix rounds, and `max_fix_attempts` is unchanged. A description-only verdict starts a description round even when the fix limit is reached, and raises no fix-limit notice while one is available. When a round completes, Foreman posts one notice, archives the CHANGES verdict and sets it aside, so the same head is reviewed again by an independent reviewer; that verdict decides. If any blocking finding is about code or tests, the existing fix round runs with all findings, as before. A third description round is refused: the description-only verdict then follows the ordinary fix path. The activity timeline lists a round as its own `Description round` entry. The review prompt still asks the reviewer to check every numeric claim in the description against the diff, and the author prompts tell the author to quote sizes and counts from the checks output, not from memory. The dispatcher gives the finding it adds for a false description claim (`reclassifyFalseClaims`) scope `description` too, whatever the claim's materiality: the round only corrects the text, and the new independent review of the same head is the safeguard.

**A CHANGES verdict carries too (issue #1048, proposal D-035).** When the latest verdict on a PR is CHANGES and the only change since is a rebase that resolved no conflict, lost nothing and left the patch unchanged (same mechanical check as D-025; CI state is not a condition), the CHANGES verdict and its findings carry to the new head with a public `Verdict carried: CHANGES` comment. The PR stays in the fix lane and no review is queued; a review is queued again only after a fix or CI-fix commit that is not a rebase (then as a fix-round re-review). A rebase with a resolved conflict, a changed patch or lost changes carries nothing and is reviewed. A carried CHANGES is not a second CHANGES round for escalation or churn. At the fix limit such a PR gets its one Needs you item at once (no final round) and is held from rebase, fix rounds and review until the homeowner decides (finish with a named list of findings, restart smaller, or close); a requested re-review lifts the hold. The carry shows on the PR card and in `team status` like a carried PASS (old head, new head, evidence).

**Carried verdicts are visible (issue #296, D-025).** A carry shows the old head, the new head and the evidence (no conflict resolved, patch unchanged, required CI green) in the dashboard queue row, the pull request row and detail page (and its timeline), and in `team status`; a record that does not match the current head is shown as such and is not merged. While a carry waits for CI the planner starts no review for that head; a refused carry (red CI, moved head, changed patch, resolved conflict) ends the hold and a full review runs. "Required CI" means every check that ran and was not skipped or neutral; skipped and neutral checks never block a carry (this repository has no branch protection).

**Rebase planning skips a deferred PR (issue #326).** `choose()` skips a PR that `rebaseDeferred` defers and goes on to the next, so the eligible conflicting PR whose issue comes first in `agents.<name>.issues` is rebased whatever order the PR list arrives in (a PR whose issue is not in the queue comes after those, then lowest PR number); a PR that `writeBlock` refuses never holds another back. The #266 rules are otherwise unchanged. When Foreman has conflicting or ready-to-implement work but plans nothing and has no job running for longer than `limits.idle_minutes` (default 30), the dashboard shows one Needs you item (`foreman-idle`) naming the work and the recorded hold reason. It clears on the first tick that plans or runs a job.

**Chained passes (issue #338).** A job that ends in one to three minutes used to leave its slot empty until the next five-minute tick. While jobs run, a tick now stays alive (holding the tick lock) for up to `limits.chain_seconds` (shipped in `supervisor/team.json`: 0, off, because a job end now wakes a pass (issue #406) and a long wait held the tick lock; the live install on Tower sets no `chain_seconds`, so it runs with the shipped 0; a live install may set a value in its host config file, which overrides the shipped one; absent or 0 = off), polling the active jobs every `limits.chain_poll_seconds` (default 10). When one has ended it runs another complete pass: ingest, allowance and budget update, plan and start, with the same leases, role slots, overall cap, open-PR cap, D-024 review independence, allowance state and self-upgrade hold. At most `limits.chain_passes` (default 3) extra passes run per tick. A tick with nothing running does not wait and does not loop, and a dry run never chains. The tick report lists the extra passes under `chained`. A self-upgrade that becomes pending during the window is seen by the next tick, so it waits at most the window.

### Notes from the issue #188 review follow-ups
- A needs-homeowner label added for a **per-day** unblock limit is removed once the UTC day has rolled over; a per-PR limit label stays until the homeowner acts. Removing a stale label is free: it is logged but does not use the per-PR or per-day unblock budget.
- With the unblock budget spent, a timed-out check (alone or beside cancelled siblings) is still treated as red after the rerun wait (cifix starts); no rerun is made and no "rerun once" notice is posted.
- The final-round scope split accepts only follow-up findings, which never hold a CHANGES verdict, so it cannot by itself clear a fix-limit rejection; in practice it duplicates the PASS follow-up issue flow. The agent's free-text reason is not copied into the issue body.
- An automatic resume keeps the count of usage-limit stops, so a job still gets at most three usage-limit waits (D-019) across the resume.
- `resumeTransient` skips jobs older than seven days and jobs that finished normally.
- Not verified against live GitHub: `gh run rerun` and `authorAssociation` on issue comments. That stays part of "verified working".

**Parallel jobs (issue #344).** Every review and split-draft job has its own worktree (`DevTest-Infrastructure-<agent>-review-<pr>`, `-split-<issue>`), so reviews no longer queue behind one shared review worktree. A new implement job is refused while its expected files overlap those of a running or already planned implement job. Expected files come from `expectedFiles(issue)` in `supervisor/team.mjs` (paths named in the issue title and body; no model call; replaceable through one function). A wrong prediction is safe: jobs never share a worktree or branch, and a real overlap shows up as a merge conflict that the existing rebase job resolves in queue order. The allowance is checked when a job is planned (planned cost counts) and again right before each start, so a limit reached mid-tick stops the remaining starts.

## Re-review after a homeowner decision (issue #366)

Reviews belong to one head and the fix limit stops new commits, so a PR stuck on a CHANGES verdict can still have a blocker the homeowner has since resolved. The homeowner records that with `ai-agent --supervisor team request-review <pr> <decision-link>`, where the link is an issue or pull request comment of this repository.

Issue #418: the command now reads the cited comment through GitHub and refuses, with a stated reason, a link that names no comment, a comment not written by the repository owner (the configured `owner_comment_review.owner`, else the repository owner), or one written before the head's CHANGES verdict. With `owner_comment_review: { "enabled": true, "owner": "<login>", "agent_logins": [...] }` in the team config, a tick needs no command: an owner comment on a PR that has a CHANGES verdict and has reached the fix limit, posted after the verdict, requests the same single re-review. It is used once (recorded by its URL), other authors and agent logins are ignored, and each open Foreman PR without a pending request has its comments read once per tick (one call). An owner comment that cannot request yet is answered with its reason: a PR notice (once per head and reason) when the head has a CHANGES verdict, otherwise only a report entry; it is not used up. Foreman's own notices are never taken as a request. It is off by default and must only be enabled once agents have their own GitHub identity (#377); until then an owner-account comment cannot be told from an agent's.

- It requests exactly one new review of the **same head**. The old CHANGES verdict is set aside only so a fresh independent review runs; it is never turned into a pass, and no review is removed. The reviewer is given the decision link as task data, and the new verdict decides: PASS goes through the usual merge gates, CHANGES stays a rejection.
- It is accepted only for an open, non-draft Foreman PR with a CHANGES verdict at its current head and the fix limit reached. A decision link can be used once per PR, and a second request while one is pending is refused, so a repeat needs a new decision.
- Foreman does not add `needs-homeowner` again for the same fix-limit stop, whatever the re-review says. The request is recorded in the state file (it survives a restart) and announced once on the PR.
- The dashboard shows the PR as waiting for the requested re-review, and afterwards as still rejected and waiting for the homeowner.

## Jobs paused on a usage limit (issue #380)
A `paused_limit` job runs no process, so it holds neither a role slot nor a place under the overall cap, and an upgrade does not wait for it (nor for any running job, issue #845). Its job record keeps its place. The worker resumes it only through a gate that (1) for a review, compares the pull request's current head with the review target and, if the head moved, stops the job (`head_moved`) without a verdict so the planner reviews the new head; and (2) checks, under one lock held until the job is marked running, that every other running or queued job leaves a free slot in the job's role and under the overall cap. When it must wait, the reason names the jobs in the way and is shown on the job (`resumeWait`) and on the dashboard card. `paused_manual` is unchanged: it still holds its slot. When eligible work finds its role (or the overall cap) full, the planner records a held reason naming the running jobs.

## Review order (issue #405)
With one review slot per reviewer, the order in which waiting pull requests are reviewed decides how long each waits. GitHub lists open PRs newest first, so the planner no longer takes that order. For each reviewer, eligible PRs (green CI, not conflicting, no verdict on the current head, not draft) are taken in this order:

1. **Starved first.** A PR that has waited for a review longer than `limits.review_starvation_hours` (default 24) goes first, the longest wait first. The wait starts when Foreman first sees the PR without a verdict on its head, survives new heads and CI runs, and ends when a verdict is recorded on the current head. No PR can wait indefinitely behind closer or scarcer ones.
2. **Scarce reviewer first.** A PR that no other agent may review (D-024 independence, judged from configured review models and head writers) goes to that reviewer before a PR either agent could review. This spends the scarce allowance where it is needed.
3. **Closer to merge.** Mergeable now, then more earlier review rounds (verdicts recorded on earlier heads), then not behind its base.
4. **Older first.** Lower PR number. A newly opened PR therefore never jumps ahead of an older PR in the same state.

**Unreviewable PRs leave the ranking (issue #1070).** A PR that no reviewer can review now (every agent has used its review attempts at this head, would be refused by D-024, or is out of allowance) is not ranked and is not shown as next, however long it has waited. It is raised on Needs you for a decision (review limit reached, or no independent reviewer) instead. Planning still visits it so each reviewer's hold reason is recorded.

The order only ranks; it never makes a PR eligible, and which agent reviews (issue #402) is unchanged. The dashboard queue and the status issue (#384) show each reviewer's order and the reason ("review order 1 of 3: only codex can review it, mergeable, older first").

**Needs you.** A fix-limit item appears only when the homeowner must act: a real CHANGES verdict on the current head (or red CI) after the fix limit, with or without the `needs-homeowner` label. A PR that reached the limit earlier but now has a new head with no verdict and no red CI is only awaiting review; it is queued, not Needs you.

**Test runs and skipped ticks (issue #448).** Full test suites share `limits.test_slots` slots (default 2, range 1 to 8; the number of suites that may run at once on Tower, which has 20 cores). A run takes a slot or waits in a first-in-first-out queue; a slot held by a dead process is free again. The install-time checks and install use it, and review and job prompts run the suite as `ai-supervisor test-slot run -- node --test …`. `ai-supervisor test-slot status` and the dashboard Supervisor page ("Test runs and skipped ticks") show what runs and what waits; `team status` prints the same. The install step has its own lock (`team/upgrade.lock`), so its test run no longer holds the tick lock or the reconcile script's lock: another tick still runs, and starts no new job while an install is in progress (the drain and swap rules are unchanged). The reconcile script's own lock now guards only the log write. A tick that does not run is never silent: the reason is appended to `team/skipped-ticks.jsonl` (`record-skip` is the command the script uses) and shown on the dashboard. A test that reaches the default dashboard start while running under the node test runner is refused unless it sets its own `DASHBOARD_LOG`, so no test can start the real server or write the live log.

**Runaway test processes (incident 2026-11-04).** `test-slot run` starts the command in its own process group with a maximum runtime (`--max-minutes N`, default 120). On timeout (exit 124), SIGINT, SIGTERM or SIGHUP the whole group gets SIGTERM, then SIGKILL after a grace period (5 s, `AI_SUPERVISOR_TEST_GRACE_MS`), and a group that outlives SIGKILL is reported; after a normal exit any member the command left behind is stopped the same way. Tests that race child processes use `tests/helpers/workers.mjs` (a ready/go barrier over stdin, no wall-clock deadline, a per-child cap, exit when the parent dies); `while (Date.now() < …)` busy-waits are forbidden in `tests/` and a test enforces it.

**Lighter test runs (issue #469).** A suite no longer starts one process per test file: `ai-supervisor test-slot run -- node --test …` adds `--test-concurrency=N` from `limits.test_concurrency` (1 to 32, default 8; an explicit `--test-concurrency` on the command wins). The default comes from the measurements below. `test_tmp_root` (an absolute path, set in `team.json` or `team.local.json`, leave it unset until the scratch pool exists: the homeowner does not want test files on the worn cache drive) becomes `TMPDIR` for the suite, so test clones and temp files stay off the RAM disk; an unusable path is ignored. Tests that make temp directories without a `t` use `tests/helpers/tmp.mjs`, which removes them when the process ends, including after a failure or SIGINT/SIGTERM (a SIGKILL cannot run any hook, so leftovers from one are caught by the sweep). `ai-supervisor test-slot sweep [--dir D] [--age-hours N] [--dry-run]` removes directories under the temp root that carry a test prefix (`supervisor-regress-`, `supervisor-test-`, `supervisor-cron-`, `supervisor-cron35-`, `devtest-broker-`, `nm-`, `gatelog-`, `hr-src-`, `hr-clone-`, `foreman-448-`, `foreman-469-`), are older than the age (default 24 hours), are not open and are not any process's working directory; if `/proc` cannot be read it removes nothing. Removals are appended to `team/test-sweeps.jsonl`. **Repeat suites.** `test-slot run` does not run a `node --test` suite again when the exact same tree already passed it: the key is the git tree hash of a clean checkout (any uncommitted or untracked change, or no git, means it runs), the command and the node version. A pass is written to `team/test-passes.jsonl` only after a real run exits 0, so every tree that is reviewed, merged or installed has passed the full suite at least once; a different tree always runs. Records older than `limits.test_reuse_hours` (0 to 720, default 24; 0 turns reuse off) are ignored, and `--no-reuse` forces a run. With `test_reuse_hours` 0 no pass is recorded at all, so turning reuse back on later finds no passes from that period (harmless: the suites just run once); `--no-reuse` with reuse enabled still records its pass. A fresh clone of the same commit has the same tree, so a fix or implement job's second run of the same tree is skipped (the skip is printed on stderr), but a review never reuses a pass: the review prompt runs `test-slot run --no-reuse`, because D-024 requires the reviewer to run the tests itself. The pass is recorded under the key computed before the run.

## Planner invariant suite (issue #1110)

`tests/planner-invariants.test.mjs` builds real `Team.plan()` inputs from named fixtures and 128 bounded combinations generated with seed `1110`. It checks each produced plan for a merge after a current-head CHANGES verdict, an action halted by the circuit breaker, and an action for a parked issue without an active PR. The harness also proves that valid and boundary plans pass and that a hand-made violation of each checked rule is detected. On failure it reports the invariant, seed and full fixture state.

Every new planner decision rule must add its invariant here, using the same state builder rather than a second planner implementation. The current planner cannot yet meet five proposed V2 rules, so they are intentionally absent rather than weakened: a conflicting PR with an unanswered CHANGES verdict can still be selected for rebase; an active PR linked to a parked issue is not excluded; a PR labelled `parked` is not excluded; a conflicting PR with CHANGES can receive both rebase and fix actions; and a red-CI PR with a current CHANGES verdict can receive both CI-fix and fix actions whether GitHub reports it mergeable or has not resolved its mergeability. The V2 planner redesign will add these rules and their generated states.

## Idle time by cause (issue #487)
Each tick snapshot records when the tick began (`startedAt`) and, for every agent idle when the tick ended, why: `upgrade` (the upgrade hold dropped work planned for that agent), `named-hold` (the planner named a hold for that agent, with its text), `work-planned`, or `no-eligible-work`. A hold belongs to the agent it names; other idle agents are not charged for it. Nothing here calls a model or GitHub: the report reads the local job records and snapshots.

### Why planned work did not start (issue #1223)
Every action the planner plans ends a tick launched or held, and a held one carries exactly one recorded reason. The tick snapshot (`dashboard/snapshots.jsonl`) and the dashboard cache (`planned`) list, per planned action, `{ type, agent, ref, outcome: 'launched' | 'held', kind, reason }`. The kinds are `slot` (a full role slot or the overall cap; a limit on the number of jobs is the same hold), `lease`, `overlap`, `allowance`, `reading_stale`, `retry_cap`, `order_guard`, `error`, plus `breaker`, `upgrade`, `host_pressure` and `admission` (the stage that dropped it). A file overlap hold names both sides by number (the held pull request and its issue, and the issue and pull request of the job it overlaps). The reason is the hold the planner noted for that one pull request or issue, never the list kept for the agent and job type, which joins the holds of other items; an action the planner noted no hold for, whose start left nothing, is not given another item's text. A planned action with no reason is recorded as `unexplained` and raised as a Needs you item of severity `action` until a later tick launches or explains it. The idle text of an agent names the hold of its own next planned action (the first one the tick did not launch), not holds of other job types. `foreman_plan` returns the recorded outcome as `lastTick` on each planned action, and `foreman_why_blocked` returns `lastTick` for the item; an action planned after the last tick says that no outcome is recorded.

A paused job's resume check that throws keeps its error message and a three-frame stack summary (redacted, 200 and 400 characters) in the job record (`resumeCheck`: message, stack, first and last time, count); the job's event log gets one `resume_check_failed` per distinct message per hour. Each tick lists the failing checks in the snapshot as `resumeChecks` (job, ref, message, consecutive ticks), and `foreman_why_blocked` for the job's issue returns them as `resumeChecks`. A check that has thrown on 3 ticks in a row is a Needs you item naming the job and the message.

`ai-supervisor team idle-report [--hours N | --from TIME [--to TIME]] [--json]` prints, per agent, minutes by cause over the range. The method is the one behind the figures in #406:
- A gap runs from the end of the agent's last job to the start of its next one. An agent with any job running is busy (a job is busy from creation to its last update; a job paused on a usage limit still counts as busy).
- Inside a gap, the interval after a tick that held the agent's work for an upgrade is `upgrade`; after a tick that named a hold for it, `named-hold`; an interval that ends at the tick that started the job is `waiting-for-tick`; otherwise `no-eligible-work`.
- From the start of the tick that started the job to the job's start is `tick-run` (the time the tick spent before the job began).
- Time with no tick record is `unrecorded`. "Idle with work available" is waiting-for-tick + upgrade + tick-run + named-hold, as a percent of the range.
The dashboard shows the last 24 hours per agent beside the agent list, and an idle agent's line names its hold ("about to start implement #5 once the hold clears; held: ...") instead of "on the next tick" when one applies.

## Implementer time with rebases on their own slot (issue #460)

`node tools/measure-implementer.mjs --from ISO --to ISO` reads the job and event records (the method of the issue's evidence: a job runs from `started` to the next run-ending event; it queues from `created` to its first `started`) and prints implementer busy time, idle time with work queued, and the time by job kind.

Window 3 Nov 2026, 14:00 to 20:00 UTC (= UK), 360 minutes, run against the live records. **Before** is what happened (rebases held the implementer slot). **After** is a replay of the same records with rebases removed from the implementer view (the rebaser slot); it is a model of the change, not a measurement after deployment. Queued intervals are not shifted in the replay, so its idle-with-queue figure is an upper bound: work that would have started at once on a free slot is still counted as waiting. Re-measure after deployment for the verified-working state.

| | before | after (replay) |
|---|---|---|
| implementer busy | 255.8 min (71%) | 180.8 min (50%) |
| implementer idle | 104.2 min | 179.2 min |
| idle with implementer work queued | 7.2 min | 0.4 min |

Implementer-job minutes by kind: fix 65.3, cifix 67.2 (fix plus cifix 51.8%), rebase 74.9 (29.3%), implement 48.4 (new work 18.9%). ## Circuit breaker for wasted usage (issue #549)

Foreman halts work that spends usage and produces nothing. A job is *wasted* when it finished (blocked, failed, or completed) after spending tokens and left no usable result: a review that blocked or completed with no recorded verdict, a verdict refused at ingestion, or a failed repair or implement job (its post-condition, a push, did not hold). A recorded CHANGES or PASS verdict, a completed repair or implement job, and a stop on the provider's own usage limit (D-019) are not waste.

- **Cause** is stable: job type plus the stop reason (`review:blocked:context_too_large`) or the validation rule that refused a verdict (`review:refused:bad-claims`). PR numbers, SHAs, claim text, tokens and cost never enter it.
- **Trip** (issue #626, D-034 proposed): 3 wasted jobs of one cause on the *same pull request* (or issue) within 6 hours, so a few cheap failures across unrelated pull requests do not trip it, or $5 of waste of any kind within 6 hours (every cause that contributed is halted in its own scope). A tripped cause stops new jobs of the job types that wasted (reviews, for a review cause). Other types keep running, including the implement job that fixes a review cause. Merges are not jobs and continue.
- **Higher limit**: $15 of waste across causes within 6 hours stops every new job. Merges and the self-upgrade (install) path are not planned jobs and continue.
- Running jobs finish; nothing is killed. A halted job type is not restarted by the transient-resume path either.
- **Clears itself**: a later job of the halted type that was created after the halt began and completes without being waste ends the halt for that cause (recorded in `resumes` with `by: success`). A job already running when it tripped does not count, and the global halt is not cleared this way. A halt holds only the pull requests or issues that wasted (those that repeated, for a count trip); the same type of work on any other pull request or issue still starts, which is how a success can happen.
- **Superseded waste does not count** (issue #865): wasted work is dropped from every evaluation, including the first after a restart or install, once a later job of the same type on the same pull request (or, with none, the same issue) has completed without being waste. A halt whose waste is all superseded ends by itself (recorded in `resumes` with `scope: superseded`). Completed non-waste jobs are kept in `breaker.successes` for this, and jobs finished before this was added are read once from their job records.
- **Resume button**: the breaker card on the dashboard has a Resume button per halt (and one for everything). It needs the D-029 access proof, a 5-second cooldown and the browser's same-origin click markers, and a dashboard running under a supervised job refuses. A click leaves a request file under `dashboard/breaker-resume/`; the next tick applies it (the dashboard never edits Foreman state). An agent or supervised job has no supported route.
- **Persistence**: the halt lives in `team/state.json` (`breaker`). Time does not expire it and a restart keeps it; a later success or a resume clears it. `ai-supervisor team breaker resume CAUSE|global|all` also clears it, and that command refuses to run without a terminal and refuses when the process descends from a supervised job (the job environment is marked and the parent chain is checked), so a supervised job has no supported route to it. `team breaker status` prints the halt and the waste by cause. Waste on file before a resume no longer counts.
- **Configuration** (`breaker` in `team.json`, overridable in `team.local.json`): `enabled`, `window_hours` (6), `same_cause_jobs` (3), `cause_cost_usd` (5), `global_cost_usd` (15), `fix_issues` (issue numbers whose implement job may start while its job type is halted). The breaker only removes planned actions. It never records, edits or loosens a verdict, a review gate or an independence check.
- **Failure**: if the breaker throws, the tick report and the Needs you list say so; existing halts stay in force and nothing new is halted or silently allowed.
- **Visibility**: the top Needs you item (cause, wasted job count, tokens, cost, affected PRs, what is still running, the exact resume command) and an Overview card with the waste by cause. Cost is the CLI's own `usage.costUsdEstimate`, shown as *usage equivalent*: plan usage is not a cash charge.
- **Replay**: `node tools/breaker-replay.mjs --from ISO --to ISO` (read-only) runs the finished job records through the same rules and prints when each limit would have tripped and the usage the later wasted jobs cost.

**Resource-aware test runs (issue #574).** `ai-supervisor test-slot run [--class small|suite|build] [--memory-mb N] [--cpus N] -- CMD` (default class `suite`) asks for a size class. Defaults: small 1 GB / 1 CPU (a single test file), suite 4 GB / 4 CPUs, build 8 GB / 8 CPUs (browser or build jobs); the owner can change them under `test_resources.classes` in `team.json` or `team.local.json`. The runner grants min(request, class cap, live headroom) or queues the job (polling, up to an hour, then exit 3). Headroom comes from a read-only JSON budget file named by `test_resources.budget_file` (`{"memory_available_mb": N, "cpus_available": N, "pressure": bool, "slice": "agents.slice"}`, written by the infrastructure side). With no budget file configured, or an unreadable one, nothing changes: no limits, no queueing, the job runs as before. While the budget reports `pressure` no new job is admitted; running jobs are never killed for that. A granted job runs in its own process group, watched against its memory grant; when it exceeds the grant the whole group is killed (exit 137), and `team/test-job-results.jsonl` records the reason, class, limit, observed size and a suggested smaller class, which is also printed on stderr. When the budget names a `slice` and systemd is present, the job also runs as its own `systemd-run --scope` leaf under that slice with `MemoryMax`, `MemorySwapMax=0` and `CPUQuota`, so the kernel kills it as a unit. Agents cannot raise caps: classes above `test_resources.max_class` (default `suite`, so `build`) are refused with exit 3 until the owner raises it in the config. The cgroup wrapper has been unit-tested only as a command line, not run on a systemd host.

**Limited test jobs and their runner (issue #598).** A memory-limited `test-slot` job runs in its own process group, so a detached watchdog kills that group if the runner disappears (SIGKILL, OOM kill). The watchdog also treats a runner that is a zombie (state `Z` in `/proc/<pid>/stat`, killed but not reaped by its parent) as gone. The job starts behind a gate (a small shell that execs the command only after the watchdog exists, and exits if the runner is gone or after 10 s), so the runner dying between spawning the job and spawning the watchdog leaves no running job (issue #659). The watchdog also compares the runner's start time, so a reused PID is not mistaken for the runner. SIGHUP is forwarded to the job only on this limited path; without a budget the runner behaves as before.

## Wake passes: work starts on events, not only on the schedule (issues #406, #338)

The five-minute schedule stays as the safety net. On top of it, four local events ask for one extra reconcile pass, so a free agent or a new card does not wait for the next fire. A wake is the same `reconcile` run as a scheduled one (upgrade step, then the team tick), so the upgrade hold, `pause`, the open-PR cap, budget and allowance modes, the circuit breaker and every other gate apply to it exactly as to a scheduled tick. Nothing in the wake path can stop a scheduled pass.

| Trigger | Raised by |
|---|---|
| `job-end` | the `worker` command, after a job's record is saved |
| `install` | a reconcile pass whose upgrade step installed new code (the pass that ran the old code dispatched nothing) |
| `inbox` | the dashboard server, when a new proposal file appears in the inbox `items/` folder (the existing write route; one directory listing every 5 seconds, no new port) |
| `approve` | the dashboard server, after a recorded Approve or Reject |

**How a request works.** A request sets one merged flag in `team/wake.json` and starts a detached runner of the *installed* code (`current/supervisor/cli.mjs`, never the code of the process that asked; with no installed copy it falls back to the asking code). Every pass, scheduled or woken, holds `team/wake-pass.lock` from start to end, upgrade step included. A runner that finds the lock held does nothing: the holder checks the flag *after* it releases the lock, so a request made at any moment of a pass, however long, causes exactly one more pass, and any number of requests are one flag. A scheduled fire that finds a pass running sets the same flag (it is not counted and not capped, since it replaces a fire), so it is never lost. The follow-up is started on the installed code, so after an install it is the new version that verifies the install. A default provider registry is never handed on (only an operator-given one), so a pass on new code loads the new version's manifests.

**Cap, storm and fallback.** Event requests are counted in a rolling hour; the limit is 40 (`WAKE_MAX_PER_HOUR`). Past it a request is dropped, the drop is recorded, and the Diagnostics page and `team idle-report` say so plainly (requests dropped, "the five-minute schedule is the fallback"). A job crash loop or repeated writes therefore run at most 40 extra passes an hour, then the schedule alone. Follow-ups cannot chain on their own: a follow-up needs a new flag, which needs a capped event or a scheduled fire. A pass lock held for 45 minutes (a hung pass) no longer holds back a scheduled pass: the schedule runs without it (the tick lock and the install lock still serialise the parts that must not overlap), while wake runners keep standing aside. A broken lock or flag file only disables the wake.

**Reads and cost.** A wake is a normal pass: it reads GitHub fresh, once, like a scheduled pass, and no read is cached. The extra cost is bounded by the cap: at most 40 extra passes an hour on top of 12 scheduled (about 4.3 times the calls in the theoretical worst case; typically a few extra passes an hour). `limits.chain_seconds` (issue #338) is not redundant yet and is not changed here. A chained tick stays alive, and so holds the pass lock, for up to 240 s while jobs run (measured: median 282 s from tick start to record over 48 hours), and a job that ends during it is served by the chain within its 10 s poll. A wake raised during such a tick is served by that same chain or, if the tick ends first, by the one follow-up pass. Where no pass is running a job end is served by a wake alone, which is the case the chain never covered. Once wakes have been seen to work in use, `chain_seconds` can be lowered or set to 0, which also frees the pass lock sooner; that is a separate change.

**Measurement.** Each recorded tick carries `trigger` (`schedule`, `job-end`, `install`, `inbox`, `approve`) and any other requests it absorbed (`merged`). A pass "did nothing" when its plan was empty. `team idle-report` and the Diagnostics page ("Passes by trigger") show passes, passes that started something and passes that did nothing per trigger, and the wake count and cap for the last hour. Records from before triggers existed carry none and are counted as scheduled; the report says how many.

**Not covered.** The install pass: the code that requests the install wake runs only after a real install, so its request is tested through the pass driver, not through a real upgrade. An install by batched installs (issues #692 and #632) is unaffected: the wake is asked after any pass whose upgrade step returned `upgraded`, whatever the batch.

## A cheap GitHub check, and a pass that ends early when nothing changed (issue #755)

**Baseline (measured on Tower, 48 hours to 6 Nov 2026 from `snapshots.jsonl` and one instrumented dry-run tick; the dry run read live GitHub and wrote nothing).** 357 recorded passes, 132 (37 %) planned nothing. Those 132 split in two: 89 had no job running and took a median 44 s (p90 143 s); 43 had a job running and took a median 284 s, because the chain window (`limits.chain_seconds` 240) waits for the running job to end. A pass that planned something took a median 301 s. One dry-run tick made 52 `gh` processes in 77 s of wall time, 71 s of it inside `gh` (3 `pr list`, 2 `issue list`, 47 `pr view`: one file list per open PR plus one lookup per prerequisite PR outside the merged window). A live pass adds one comment read per open PR (inferred from the code, not counted). Local work (ingest, retries, the state files) was not separately timed; the figures above bound it to a few seconds (inferred).

**The check.** At the start of a **scheduled** pass (never a wake) Foreman sends REST conditional requests, `If-None-Match` with the stored ETag, through `gh api -i`; a 304 is the unchanged answer and does not count against the rate limit (observed: the remaining count did not move on 304s). It covers:

| What the planner reads | Endpoint watched |
|---|---|
| issues, their bodies, labels, state, comment counts; PR state, merge, closure | issue list sorted by update time, first 100 (every comment, label, push, review and merge moves an item to the top, so the page changes) |
| open PRs: heads, drafts, titles, base | open pull list |
| label names | label list |
| comment text, including an edit | newest 5 issue comments by update time |
| review line comments | newest 5 PR review comments by update time |
| what is mergeable | tip of `main` and of every other base branch of an open PR |
| check state of each open PR head | `check-runs` and combined `status` of each head |

**Not covered by an ETag, and treated as changed, never guessed:** more than 99 open PRs or more than `change_check.max_open_prs` (40) heads (paged; not `limits.max_open_prs`, the open-PR cap for new work); a stored PR whose mergeability is `UNKNOWN` (GitHub computes it lazily, with no change to anything above); a missing, corrupt, foreign or future-dated state file; any error, timeout, odd status, missing ETag or a 304 without a stored ETag. Not covered at all, and left to the forced full pass: a deleted old comment or issue outside the newest page, a repository setting change. PR reviews are not read by the planner (verdicts are comments), and a review submission moves the PR in the issue list; the exact GitHub behaviour for an edited review is assumed, not verified.

**An unchanged pass is a replay, not a skip.** The pass runs exactly as before, ingest, retries, breaker, allowance, stuck-check timers, self-check, status record and the upgrade step included, but its read-only GitHub calls are served from the data the last full pass stored (`team/gh-cache.json`), which the 304s just proved identical. A GitHub write during the pass turns the cache off for the rest of that pass. If the replay planned nothing, ingested nothing, notified nothing and skipped nothing, it ends there, without entering the chain window, and is recorded `noop` (a job end asks for its own pass, issue #406; past the wake cap the schedule is the fallback). If it did anything it is an ordinary pass. Nothing local is skipped, so nothing time-based can be lost:

| Work on the pass | On an unchanged pass |
|---|---|
| job timeouts, dead-worker detection, lease release, recovery, due restarts (`reconcileOnce`) | runs first, before the check, always |
| self-upgrade step, `min_install_gap_minutes` batching (off by default), hand-install hold, watchdog | runs, untouched (it does not use the cache) |
| ingest of finished job results, retries that came due, owner-comment scan, inbox proposals, Approve/Reject | run on the local files; their GitHub reads come from the cache, their writes are real |
| allowance and budget readings, due probes, breaker evaluation and clearing, self-check, idle tracking, stall and stuck-check timers | run against the current clock and local state; stuck-check age is computed from the current time on the cached rollup |
| dashboard record, snapshot, status issue | written as usual; the data was verified a moment ago |
| the chain window (waiting for a running job to end) | skipped only when the replay did nothing |

**Fail safe.** Any doubt gives the full pass, as before. A failed check is never a failed tick: it is recorded as the reason, and a connection failure during it cannot be counted against an install (it never reaches the install verification). The baseline ETags are taken before the full pass reads anything and stored only after it read everything without error, so a change that lands mid-pass can only make the next check say "changed". Every `change_check.force_full_minutes` (default **30**) a full pass runs whatever the check says: it bounds how long a change the ETags cannot see (above) stays hidden to six scheduled passes at five minutes and two at fifteen, and costs one full pass in six. It also keeps `getMergedPull` and file-list lookups cheap on full passes: a merged PR and a PR's file list at a given head cannot change, so they are remembered (`memo`) across passes.

**Config** (`change_check` in `team.json`, overridable in `team.local.json`): `enabled` (true), `force_full_minutes` (30), `max_open_prs` (40; the number of PR heads the change check will page, unrelated to `limits.max_open_prs`), `timeout_seconds` (30).

**Measurement.** A pass record carries `noop`, `ghCalls`, `ghMs` and `check` (`result`, `reason`, `probes`, `served`). Diagnostics ("Passes by trigger") and `team idle-report` show no-op passes per trigger, the median duration of a no-op against a full pass that did nothing, and the median `gh` processes per pass. Compare before and after install with `ai-supervisor team idle-report --hours 48`.

## Review follow-up batching and the churn stop (issue #864)

- A PASS review's non-blocking findings are not given an issue each. They are added to one open issue per area (the top-level directory holding most of the PR's changed files; `general` if the file list is unreadable), marked `devtest-followup-batch v1 area=<area>`. A later review of the same area updates that issue; a finding already listed is not repeated, and a review job is never added twice. A new batch issue is opened only when a reviewer-written follow-up is in it; a list of only immaterial description-claim notes joins an existing batch and otherwise stays on the review comment. Because one issue holds the area's follow-ups, one implementer run clears several.
- A fix-round re-review first judges whether each previous blocking finding is resolved. A new blocking finding is allowed only for a real defect in lines the fix changed; anything else is a follow-up.
- Churn: when the last two re-reviews of a PR each drew blocking findings that repeat nothing from the round before, Foreman starts no further fix job for it and raises one Needs you item (the needs-homeowner flag and a PR notice) with the three rounds side by side. A new head that is reviewed PASS clears it. At the fix limit the ordinary fix-limit item applies instead.

## Done is installed and verified, not merged (issue #855)
Merged is a stage, not the end. Each issue moves through **merged** (the pull request is in `main`), **installed** (the installed commit contains it and the live tick on the new version was fine) and **verified** (the issue's live checks passed on the installed version). An issue with no live checks stays at installed. Foreman owns every step the change needs, including the ones outside the repository:

- **A local setting** ships as a migration (`supervisor/migrations/NNN-name.mjs`) that applies it at install ([Config migrations](#config-migrations-on-install-issue-153)).
- **A value specific to this host** that must not go into this public repository (today: an origin for `dashboard.allowed_origins`) is observed by Foreman: the dashboard records the Origin of a refused write, and the tick raises exactly one inbox item with that value filled in (one at a time, never again for the same value). Approving it backs up `team.local.json` (mode 600), merges the value, validates the result and checks the written file parses, restoring the backup if it does not. The overseer cannot submit this kind of item.
- **A check that needs the running system** is listed under a `## Live checks` heading in the issue, one per line: `- GET /path -> 200` or `- GET /path -> 200 contains "text"` (GET, HEAD or POST; a path relative to the dashboard, at most ten; only the repository owner's issue text is read). After the install that contains the change, Foreman runs them against `self_upgrade.public_dashboard_url`. All pass: verified. Any failure, including an unreachable system, opens a follow-up issue with the evidence for the installed commit and the issue stays unverified; the checks run again after the next install. A failure is never a manual note.
- **Reviews block on a missing step.** The review prompt makes a setting, migration or post-install action that the pull request does not deliver a blocking finding. Foreman also scans the pull request description: a line such as "the homeowner can set X after deploy" turns a PASS into CHANGES with a blocking finding.
- **Truly manual steps are explicit and rare.** A step that needs the homeowner's credentials or a physical action goes under a `Homeowner steps` heading in the pull request description. Foreman records it and the dashboard shows it in Needs you for that pull request. A step that could have been automated is not acceptable there; the reviewer blocks it.

## The inbox lane (issue #971)

An approved overseer prompt (D-031) runs in a lane of its own, so it never waits behind implement work.

- **Own slot.** `limits.roles.inbox` (default 1). The lane is not part of `limits.overall` and implementer, reviewer and rebaser jobs never fill it. A prompt starts on the next tick when the lane has a free slot, whatever the other slots are doing. Allowance, usage-limit, model (no Opus writer) and circuit-breaker rules still apply. The host-load admission check is a separate issue and is not part of this change.
- **Report contract (issue #1147).** When `reports_dir` is configured, Foreman appends one contract to every Inbox prompt (text in `supervisor/inbox-report-contract.txt`, code in `supervisor/inboxreport.mjs`): write the report to `inbox-<first 8 characters of the item id>.md` in the reports folder, first line `STATUS: done|nothing_changed|failed`, last line exactly `<!-- foreman-report: finished -->`. It is added once; a prompt that already holds the same text is not changed. When the job ends in any way (completed, failed, cancelled or stopped at the time cap), Foreman reads the tail of that file: marker on the last non-blank line (trailing whitespace allowed) means finished and adds nothing; any other ending adds "Report <file> is unfinished" to the Inbox result, and no file adds "Report <file> is missing". The note never changes the item's done or failed state. `foreman_reports` keeps flagging missing markers as before.
- **Order guard (issues #971, #1238).** Keywords cannot tell which prompt changes queue order or config ("Swap 940 and 935", "Skip 935"), so the guard fails safe: while an approved prompt is unstarted, or a prompt is running (including one the fast start path began during a pass and the next pass has not adopted yet), no new implement job is handed out. The hold names what it waits for and what ends it ("waiting for an approved inbox prompt \"…\" that changes queue order or config; new implement work starts after it has run, or when it is rejected or undone, or N minutes after it was approved"). A prompt is exempt, and never sets the order mark, when its item says `effect: read_only` or `effect: report_only`. The guard also ignores an approved prompt that cannot start now (a circuit-breaker halt that covers prompts, every agent at a usage limit, an unusable worktree), a prompt approved more than twice `limits.inbox_max_minutes` ago, and a job record older than twice the cap. An implement-job halt does not block a prompt (the breaker blocks a prompt only for the global halt, a halt whose cause includes prompt jobs, or a prompt that is itself an implement job). Reviews, fixes and rebases are unaffected. The fast start path (`startApprovedNow`) follows the same lane rule as the planner: the inbox slot count only, not the implementer slots, `limits.overall` or the open-PR pause. The queue view lists an approved prompt as "Inbox lane".
- **Hold cycles (issue #1238).** Each tick, before planning, Foreman lists the holds that wait for something (`supervisor/orderguard.mjs`, `supervisor/holdgraph.mjs`): new implement picks wait for each guarding prompt, and a prompt stopped by a halt waits for that halt to end (for a halt of implement jobs, for an implement job to succeed). When two holds wait for each other the lowest priority hold (the order guard) is dropped, the tick report lists it under `holdCycles`, and one Needs you item `hold-cycle-<prompt>` at action severity names both holds. A hold that has lasted more than 30 minutes shows as a `stalled-hold-…` item with its owner and the control that clears it, by reason: an order guard hold (owner overseer; reject or undo the prompt on its Inbox card), a circuit-breaker halt (owner homeowner; Resume on the Breaker card), every agent at a usage limit (ends when the limit resets, or reject or undo the prompt), an unusable worktree (owner overseer; repair or remove the worktree, or reject or undo the prompt). A prompt the guard ignores because it cannot start is not reported as an order guard hold. The overseer declares `effect` through `foreman_propose` (kind `prompt`, optional `read_only` or `report_only`); the approval card tells the homeowner about the declaration before approving.
- **Time cap.** `limits.inbox_max_minutes` (default 15, 1 to 720). A running inbox job past it (running time only; a usage-limit pause does not count and a resumed job counts again from the resume) is stopped once; its item ends `failed` with the cap named.
- **Visible.** The item reads queued for the inbox lane, then running in the inbox lane, with the time it waited (`lane`, `waitedMs`, `startedAt` in its status file). The slots list and job cards show an "Inbox lane" role.

## Infrastructure faults never use attempts (issue #1107)

An attempt is a real try at the work. A job stopped by a sign-in problem, a launcher failure, a usage limit, the network, a provider outage or the host has not tried the work, so it never counts toward a review, fix, rebase or continue attempt, a retry cap (`max_same_cause_attempts`), the circuit breaker or the fix limit.

- **One classifier.** `supervisor/faults.mjs` (`classifyEnd`, pure) puts every job end into a work outcome or an infrastructure fault with one cause from a fixed list: `auth_error`, `launcher`, `usage_limit`, `network`, `provider_outage`, `host_resources`, `other_infra`. A stop only an agent run can produce (post-condition not met, context limit) is work. Any other unknown end is work only when tokens were spent; a missing or malformed record, or an end with no tokens, is `other_infra`. A deliberate stop is neither.
- **No attempt is used.** `supervisor/faultflow.mjs` hands the launch's attempt back, skips the retry-cap count, the breaker waste record and the failure-cause record, and sends no needs-homeowner notice (a usage limit keeps the D-019 flow). An implement job that never started is queued again.
- **The agent is parked, not the item.** The planner treats a parked agent as out (like one out of allowance), so another eligible worker may take the item. A usage limit is not parked here; D-019 holds the agent until the reported reset plus 2 minutes.
- **Probe without a model call.** A parked agent is checked with its provider adapter's `preflight` (sign-in status and launcher) at 5, 15, 30 and 60 minutes, then hourly, and is released when the check passes. A fault soon after a release continues the earlier one.
- **The homeowner hears once.** One Needs you item per parked agent (`agentfault-<agent>`), raised only when the fault has lasted 30 minutes. It names the cause, since when, the items waiting and the fix (for a sign-in problem: sign the named CLI in on Tower), and clears itself when the check passes.
- **Install.** Retry caps whose cause is an infrastructure cause (`auth_error`, `preflight_failed`, `network_error`, `usage_limit`, `transient_rate_limit`) are cleared once, one report line each (`infraCapsCleared`).
- **Status.** `foreman_status` (`infraFaults`) and the dashboard's robustness view list fault counts, parked agents and recent faults apart from the work failure causes.
- **A stop is a decision (issue #1109).** `ai-supervisor stop` (and the dashboard's stop action) write the stop on the job record (`stop: { by, reason, at }`) and clear `autoRestart` and `autoResume` BEFORE the worker is signalled, so a worker that ends first cannot overwrite it (`supervisor/stopjob.mjs`). The classifier reads the marker: the job is neither work nor a fault, uses no attempt (the launch's attempt is handed back), does not park the agent and does not feed the breaker. A stop with another reason, such as the idle timeout, stays a work outcome.
- **Install release (issue #1109).** Once, on install, every attempt that a finished job used for an infrastructure fault or a stop is released from its counter (review, fix, rebase and continue attempts), one report line per job naming the pull request (`infraAttemptsReleased`). A job that did real work keeps its attempt; each job is released at most once, so a rerun changes nothing. This is what frees a pull request whose per-head review attempts were spent by sign-in failures.
- **Visible.** Each job description ends with a note (for example "stopped by homeowner; no attempt used, agent not parked, automatic restart off"), so `foreman_jobs` (`summary`) and the `jobs` of `foreman_why_blocked` show it.

**Skips are not errors (issue #1119).** A tick separates real errors from deliberate skips. A skipped item names its kind in `deliberate`, one of `usage_limit`, `reserve`, `parked_agent`, `admission_refusal` or `dependency_wait` (code: `supervisor/tickskips.mjs`). Tick status `ok` means no real error: deliberate skips are listed with their reasons under the tick's `skips` and never change the status. Status `error` means an exception, a failed read or a failed launch, or a skipped item with no kind. An item with an unknown kind is an error and the reason names the unknown kind, so it is never hidden. The install's live-tick check uses the same rule: it fails only on a real error, so an agent out of allowance cannot roll an install back. The Supervisor health view and the scheduled run's exit code use the same rule: a skip-only tick is `ok`, lists its skips, and exits 0. A parked agent is a `parked_agent` skip.

A rollback latch written before this change whose only cause was a usage-limit refusal (reason `live tick failed: not started: <agent> reached its usage limit ...`) is cleared once by the new code, with a `latch_cleared` upgrade record, and the pending install then proceeds. The installed version before this change refuses to install while any latch exists, so it cannot reach that code by itself.

The old latch records only the first fault of the failed tick, so a tick whose first item was a usage-limit skip and whose later item was a real error also looks skip-only and is cleared. The install is checked again by a live tick under the new rule, so a repeat of the real error fails it.

**Homeowner steps.** On a host that is latched now, reach this change by `clear-latch` (or a hand-install, which has no latch check); the automatic install then proceeds. A latch with another cause (for example `upgrade script failed: swap: version already installed`) is not cleared by this change and needs `clear-latch` once the cause is understood.

## Clearing the upgrade latch from the dashboard (issue #1160)
After a rollback, or a homeowner pause that sets the latch, automatic upgrades stop until the latch is cleared. The Needs you card `upgrade-latched` now says why and carries the control, so no Tower prompt is needed.

- **The card** shows why the latch was set: for a rollback, the versions it went from and to and the failed check; for a homeowner pause, the first three lines of the stop record the reason names (read only from the stop directory, `STOP_DIR` or `/mnt/cache/logs/agent-cleanup`, directly inside it, never through a link). It also shows when the latch was set and what would install next: how many commits main is ahead of the installed version.
- **The control** is the inbox action `clear_latch` (no target). A click, or the homeowner's approval of an overseer proposal made with `foreman_propose` kind `action`, leaves an approved item; the next tick runs it once, as for every inbox action (`running` is recorded first).
- **Refusals change nothing and end the item `failed` with the reason:** no latch is set (a stale card: it was cleared by hand or by the old `clear-latch` command first), an install is running (`upgrade.lock` is held), a hand-install holds the host, or an install waits for its verification. The action runs while holding `upgrade.lock`, so it cannot race an install.
- **Record.** The action removes the latch file and appends a `latch_cleared` line to `team/upgrades.jsonl` with the time, `by` (the homeowner), the reason text (the click or the proposal), and what the old latch said. The next tick may then upgrade under the existing rules; nothing is installed by the action itself. The overseer can propose it but cannot approve it.
- **Homeowner steps.** None on Tower: open the dashboard, read the card, press Clear upgrade latch. `ai-supervisor self-upgrade clear-latch` still works.
- **Job commands take the short id (issue #1160).** `pause`, `stop`, `resume`, `logs` and `release` (as `status` already did) accept a unique prefix of at least 8 hex characters of the job id, as the dashboard and Inbox show it; an ambiguous prefix is refused with `job ID prefix is ambiguous`.

## Host pressure hold uses real memory pressure (issue #1151)

Foreman starts no new job while starting one would hurt the host. The hold has three measures, each with a threshold in `team.json` under `host_pressure` (defaults shown; every key is optional):

| Key | Default | Holds starts when |
| --- | --- | --- |
| `disk_percent` | 80 | the root volume is used above this percent (unchanged from issue #1007) |
| `swap_pages_per_second` | 200 | swap pages in plus out per second, averaged over the window, are above this |
| `swap_window_minutes` | 5 | the averaging window; no swap verdict until the recorded history covers half of it |
| `min_available_mb` | 1024 | available memory (`MemAvailable`) is below this |
| `swap_warn_percent` | 90 | never: swap used above this is a warning on the Health page and in `foreman_status`, and does not hold starts |

Swap used percent alone never holds starts: old pages can sit in swap for weeks with no activity (10 Nov 2026: 92% used, zero pages per second, 7.9 GB available, and Foreman started nothing). Swap activity is read from the cumulative `pswpin` and `pswpout` counters in `/proc/vmstat`; each tick keeps its samples in `state.hostPressure`, and a counter that went down (reboot) restarts the window.

One source for the reason. The tick records the verdict in `state.hostPressure` before it plans. Every planning run (the tick, the dashboard, `foreman_plan`, `foreman_why_blocked`) then marks each planned job start with that text (`heldBy`, and as `why`), replaces the agent's other planner holds with it, and appends it to the agent's queue entries. So the agent idle line, `foreman_status`, `foreman_plan`, `foreman_why_blocked`, the Next card and the review order all say "host pressure: swap activity is 500 pages per second over 5 minutes (limit 200)" instead of a leftover allowance-mode text. A record older than 30 minutes is ignored. The Needs you item (`selfcheck-host-pressure`) names the measure and its value. The Health page and `foreman_status.hostPressure` show every measure next to its threshold.
