# Team dashboard (issue #32)

Status: implemented in source on `claude/issue-32-p0-team-dashboard`; **not deployed**, no screenshot yet (see Evidence).

One read-only page that shows what the agents are doing, so the homeowner need not run supervisor commands. It is part of the supervisor payload (`supervisor/dash*.mjs`), so the existing upgrade path installs it and history survives upgrades.

## What it shows
Needs attention (pinned, red) · Agents now · Queue per agent (the dispatcher's own `Team.plan()` run over cached data, plus a reason for every issue and PR) · Usage · Graphs · the last 50 events. All values come from the supervisor's job records, the team state, and the cache and history that the tick writes.

Attention rules: `needs-homeowner` issues; blocked or failed jobs (last 48 h, unless superseded by a newer job on the same issue); failed tick with time and redacted error; no tick for more than 10 minutes (or none ever); red CI on a non-draft open PR; an agent idle while the plan has work for it (same plan seen idle in snapshots spanning 9+ minutes, or the loop disabled); and **a `paused_limit` job on a `usage_limit` event while the provider's own newest allowance record shows no exhausted window** (the 13:15 case: 34% session, 18% week). With no allowance data the pause is flagged as unverifiable, not as wrong.

## Constraints and how they are met
- **Read-only:** GET and HEAD only (405 otherwise) except the form POSTs to `/mark-read`, `/watch`, `/probe`, `/inbox` and `/breaker-resume` (each behind the write protection of D-029). The dashboard modules import no process spawner, GitHub client or network client (a test asserts this, and another shows `gh`, `claude`, `codex`, `git` and `curl` are never started when the page loads).
- **Circuit breaker Resume (issue #626, D-034 proposed):** the breaker card shows a Resume button for each halt. `POST /breaker-resume` needs the access proof, a 5-second cooldown and the browser's same-origin user-click markers, and is refused by a dashboard under a supervised job. It only leaves a request file in `dashboard/breaker-resume/`; the next tick clears the halt. A halt also ends when a later job of the halted type succeeds.
- **Overseer inbox (issue #124, D-031 proposed):** when `inbox.dir` is set in `team.local.json`, each pending overseer proposal is one Needs you card showing its exact text with Approve and Reject buttons. They post to `/inbox`, protected like the other writes (Host, Origin, the secret proof, a one-second cooldown). The route records a decision only; the next tick acts on an approval. See [foreman-mcp.md](foreman-mcp.md).
- **Spends no tokens:** the page makes no GitHub or model call. The five-minute tick (`reconcile` → `team tick`) refreshes `dashboard/cache.json` (compact PR and issue data, no bodies or comments) and appends one snapshot to `dashboard/snapshots.jsonl` under the supervisor state root (`/mnt/cache/ai-supervisor/`). Retention: 35 days and 12,000 snapshots, trimmed about hourly, hard cap 16 MiB. The cache is also written when the loop is disabled or a tick errors, so "no tick for 10 minutes" is detectable; a disabled loop is reported as disabled, not stale. Dry-run ticks write nothing.
- **Usage is never estimated:** allowance windows come from the structured data of #21 (`job.allowance`) and, for Codex, from a model-free probe (below); each card shows the **last known reading with its age and source**. "Unknown" appears only when no reading was ever reported.
- **Stale and missing readings (issue #75).** One rule everywhere (`windowExpired` in `supervisor/allowance.mjs`): a window whose provider-reported reset time has passed is *expired*. It is greyed on the card ("reset 1h 17m ago; current use unknown"), never counts as evidence of a limit or of capacity in the Warnings rule, is ignored by model routing, and is not drawn on the chart past its reset: the line ends at the last sample before the reset, an *Expected reset* marker sits at the reported time, and a later reading starts a new segment. A record with no windows (Codex at the moment it hits its limit reports `primary: null, secondary: null`, captured as `tests/fixtures/allowance/codex-0.166.0-exec-limit-hit.token_count.json`) is status `unknown`, not a reading, and never hides an older reading. A limit pause shows "Limit reached, resets <time>" with its basis: the reset time reported with the limit, else the reset of a full, current window in the last reading, else "reset time not reported", plus when the supervisor retries. The Warnings rule ignores a capacity reading taken before the pause, and says when the full window has reset since ("the limit may be over"), always quoting the last reading and its age.
- **Model-free probe (Codex only).** Each tick reads the newest twelve Codex rollout files of the last two days (`~/.codex/sessions`, tails only, `token_count` `rate_limits` counts only, never message text) and keeps the newest record that has windows in `dashboard/cache.json` (`probes`), timed by the record itself. Codex writes these records for every session on Tower, so a paused agent's reading refreshes whenever any Codex session runs. It cannot see usage made elsewhere. Claude Code has no model-free source (its limits arrive only in a live `stream-json` run), so a Claude reading refreshes only when a Claude job runs, and is marked expired once its reset passes. Tokens and the CLI's own cost estimate are read from the provider's structured `result` / `turn.completed` line (`supervisor/usage.mjs`: counts only, never message text) and labelled "estimate, not billing". A result line longer than the 16 KiB line bound is not parsed, so those tokens show as unknown.
- **No secrets:** every free-text value passes `redact()` (emails, token shapes, bearer values, long opaque strings). Prompts, session ids and raw output are never read.
- **Hosting:** Node built-ins only. Binds to **one private LAN IPv4 address** (RFC 1918, not network or broadcast); wildcard, loopback, public addresses and names are refused. The Host header must equal `<address>:<port>` (DNS-rebinding guard). Self-contained: inline SVG and CSS, a 60 s page refresh (driven by the page script so an in-place table address is kept; a `<noscript>` meta refresh without script), strict CSP (`default-src 'none'`).
- Merge history for the graphs (`mergeLog`: PR, issue, agent, start and merge times) is recorded in the team state from this change on; earlier merges are absent, and the graphs say "no data yet" rather than guess.

## Estimated finish time (issue #156)

Each queued issue and open PR shows `est. HH:MM–HH:MM` (p50–p90) on the Next panel, the Work queues and the agent queue table, and `team status` prints the same text under "Estimated finish". Hovering shows the basis. The estimate is computed by `supervisor/estimate.mjs` from Foreman's own records only (no model or GitHub call):

- Step durations (implement, continue, review, fix, ci-fix, rebase) are the recorded `updatedAt - createdAt` of completed jobs; "CI" is the gap between a producing job ending and the next review of that PR starting. Percentiles are nearest-rank.
- Fix rounds: the chance is the share of reviewed PRs that got a CHANGES verdict. The p50 path includes a fix round (fix, CI, re-review) at 50% or more, the p90 path at 10% or more.
- Items are placed in queue order into the role slots and the overall cap; running jobs hold their slot for the rest of their typical time; the merge happens on the next tick.
- If an agent is out of allowance, or its forecast runs out before a step would start, that step moves to the reset time and the estimate says "(after Wed 07:18 reset)".
  A forecast stands for running out completely, so it holds every step, reviews included, to the reset. An agent in `reviews_only` mode keeps its review, fix, CI fix and rebase steps and only its implement and continue steps move.
- The budget reason (the "Why:" line) says which rule applied (issues #627, #680): "at or above 85% with more than 24h to go" (the default values of high_water and high_water_min_hours), "the reviews-only latch was released by a fresh allowance probe", or the estimate at reset, which is for information only and never sets a mode. Details and settings: [allowance-scheduling.md](allowance-scheduling.md).
- Known waits are listed with their own time: CI running, the allowance reset, and the self-upgrade rate limit ("upgrade waiting, next try 22:30").
- A step type with fewer than 5 recorded jobs shows "no estimate yet" rather than a guess.
- **Wide ranges are left out (issue #413).** The dashboard shows a range only when its width (p90 − p50) is no more than 50% of the time from now to its midpoint (`MAX_RANGE_SHARE` in `supervisor/estimate.mjs`). A wider range, such as 08:58–16:10 for a job starting this tick with no history, is omitted from the Next panel, the queues and the agent table without replacement text; known waits still show. `team status` prints the stored text unchanged.
- The Next card no longer repeats the next-tick countdown; the app bar shows it, and its "none" stands when no tick is scheduled.

## Needs you panel (issue #141)

The panel lists every open item that needs the homeowner, derived from the cache and job records on each render, so a card clears as soon as its cause does. Sources today: open issues and PRs labelled `needs-homeowner`; PRs at the fix limit (still rejected) or the review limit; blocked or failed jobs whose issue or PR is still open; a rebase that dropped commits; a failed config migration; a failed tick; and open issues that are in no agent's queue. A red-CI warning on a PR at the fix limit becomes the fix-limit card. Each card carries `text` (what happened), `tried`, `decision` (the one action) and `links` (PR, job). The header shows `Needs you (N)` instead of Idle while any card is open. When the event log (#100, #106) lands it replaces the sources and keeps this card shape.

A fix-limit or review-limit card is held back while a final job for that PR is still active: a `review`, `fix`, `cifix` or `rebase` job that is queued, running, `paused_limit` or `paused_manual` (issue #184). The card returns as soon as the job reaches a terminal status (`completed`, `failed`, `blocked` or `stopped`), so the hold cannot stick. A paused job is not hidden meanwhile: it stays on its agent card with a paused marker, and the header reads `Paused` unless a higher-ranked state (Needs you, Stuck, Unknown) applies. A job left paused by hand therefore delays the limit card but never leaves the page without a signal; the job will still use its attempt when resumed. Tests cover each status and kind and the return of the card.

## Stale server after a self-upgrade (issue #155)

A verified supervisor self-upgrade also restarts the dashboard server: the upgrade step finds the `cli.mjs dashboard serve` process (never a worker, tick or job), stops it, starts the same `--host` and `--port` from the new version, and records `dashboard_restarted` (or `dashboard_restart_failed`, with an alert) in `team/upgrades.jsonl`. If no dashboard server is running it does nothing. This code lives in `supervisor/upgrade.mjs`, an upgrader path, so the first deployment is by hand.

Restart details (issue #193): the new server must still be running (and, where a health check applies, still answering) after a short grace period, otherwise it is stopped, the old version is started again and `dashboard_restart_failed` is recorded. The intent to restart is saved before it runs, so a tick that dies between the `verified` record and the outcome record is retried on the next step. The production dashboard (AI Dashboard user script) runs `node /mnt/cache/ai-supervisor/current/supervisor/cli.mjs ...`, so its version reads as unknown and the first verified upgrade always restarts it; that is harmless. The restarted server gets only `PATH`, `HOME` (and `DASHBOARD_PORT` if set) and appends its output to `/mnt/cache/ai-supervisor/dashboard.log` (override: `DASHBOARD_LOG`), like the user script.

An agent is shown as Unknown while a job record it cannot read or understand is less than 7 days old; the warning names the file. An unreadable record has no id, so it is not counted against a role slot (only unknown-status records whose id is in team state are). Case 3 of issue #155 (the "Upgrade waiting" badge) is not implemented; #155 stays open.

Until the server is on the installed version, the Warnings panel shows "Dashboard is running <old>, Foreman is on <new>; what you see may be out of date." The server re-reads `team.local.json` on every request (a bad edit keeps the last good configuration). A job record whose status this version does not know, or that cannot be parsed, shows the agent as **Unknown**, never Idle.

## Watching a job (issue #123)

Jobs run headless, so the supervisor keeps a per-job **transcript** at `<state>/transcripts/<job id>.jsonl` (directory 0700, file 0600). It is separate from the classification-only event log, which is unchanged.

- **Schema.** Each adapter maps its stream to one entry shape (`kind`: assistant, tool_call, tool_result, usage, system, log, truncated; plus `tool`, `text`, `detail`, `tokens`, `evidence`). Claude and Codex are mapped in `supervisor/adapters/*.mjs` (`transcript()`); a new provider adds one function. Reasoning/thinking is not recorded.
- **Redaction before writing** (`supervisor/transcript.mjs`, tested with a seeded canary per form in `tests/transcript.test.mjs`). Replaced before anything reaches disk: the values of secret-named environment variables (also in JSON-escaped form); token shapes (GitHub, OpenAI/Anthropic, Slack, GitLab, npm, AWS keys, JWTs, OpenBao `hvs.` tokens, long random runs that mix letters and digits; not paths, Git SHAs or plain identifiers); private key blocks; OpenBao paths (`bao://`, `/v1/secret/...`, `secret/data/...`) and `BAO_*`/`VAULT_*` settings; URL userinfo; `Authorization` and `Proxy-Authorization` of any scheme and `Bearer` tokens; `mysql -p<value>` and `-u user:<value>`; `bao`/`vault` Key/Value tables. One scanner handles every pair whose name is secret-named, in any case: `NAME=value`, `name = value`, `?name=value` in a URL, `name: value` (YAML and headers such as `Cookie`, `Set-Cookie`, `X-Api-Key`; to the end of the line), `"name": "value"` (plain or escaped JSON) and `--name value` / `--name=value`. A name is secret-named when it contains password, passwd, passphrase, secret, token, api key, private key, access key, credential, cookie, session id, authorization or bearer, or has pass, pwd, pw or auth as a whole segment (`DB_PASS`, `HA_PW`; not `PWD` or `GIT_AUTHOR_NAME`), or ends in `_key`/`Key`. A count such as `input_tokens: 1234` is kept. **Dropped whole:** the result of a call that reads a secret: `bao`/`vault` `kv get`, `read`, `login`, `token lookup`, `-field`; an OpenBao HTTP API call (`/v1/<mount>`, `X-Vault-Token`/`X-Bao-Token`, `$BAO_TOKEN`); a delivered secret file (`/secrets/`, `/run/secrets/`); `.env`, `secrets.yaml`, `.netrc`, `.git-credentials`, `credentials`, `*.token`; `printenv` or `echo` of a secret-named variable. A result that cannot be paired with its call is dropped too. **Not covered:** a secret with no recognisable shape or name (for example a bare password in prose, `password is X`, or printed by another command); redaction is pattern-based, so treat the page as sensitive and keep it on the private network.
- **Cap and retention.** 4 MiB per job. At the cap whole entries stop, one `truncated` notice is written, and only the lines that triggered a classified event may still use a 64 KiB reserve. Files older than 7 days are deleted when the next job starts.
- **Watch view.** `/jobs/<job id>` shows assistant messages, tool calls as one expandable line each, running token count and elapsed time. For a running job `watch.js` follows `/api/jobs/<id>/events` (server-sent events, `Last-Event-ID` resume, polled every 250 ms, so new lines arrive well inside 2 seconds). Both are GET-only and read-only. The page is complete without script; the server and the browser render with the same functions (`dashui/watch.mjs`), so a replay equals the live view.
- **Entry points.** A running agent card ("Watch live"), the Job history and Activity tables, and each Needs you item that comes from a failed job ("Replay transcript").
- **Classifier evidence.** The exact line behind a classified event (usage_limit, crash and so on) is stored with the entry and highlighted.

## Unreachable page and the restart gap (issue #432)
`supervisor/dashui/unreachable.html` is a self-contained page (inline style, script and SVG donkey; nothing from outside) for the time the dashboard does not answer: "The donkey's being reshod. Back shortly." It polls `/api/view.json` on its own origin every 4 s and reloads the same URL when that returns 200 with a JSON content type (a proxy's HTML error page does not count). A loop guard (sessionStorage, per tab) stops reloading after 3 reloads within a minute and checks once a minute instead, so a proxy that serves this page on some paths while view.json is healthy cannot cause a reload loop. After 5 minutes the text becomes "This is taking longer than an install should." It never says an install is running, because it cannot know. `tests/dashboard-unreachable.test.mjs` pins the wording, the absence of external resources and the polling and timing; `tests/unreachable-visual.mjs` (Tower only) captures both messages at desktop and phone width.

**Nothing serves this page yet.** The file exists; wiring it in is separate (see options below and the proxy note).

### Can the old server stay up until the new one is ready?
Today `restartDashboardServer` (`supervisor/upgrade.mjs`) stops the old server, waits for exit, then starts the new one on the same host and port. Findings (Node v22.18.0 on Tower, checked with a small script):
- **`reusePort`**: `listen({ reusePort: true })` is accepted on Node 22.18 (Linux). Two servers that both set it bind the same port. A new server with `reusePort` cannot bind while the old, already-running server did not set it: `EADDRINUSE`. So it works only from the version after the one that adds the option; the first upgrade still has the gap. Also the kernel then spreads new connections across both servers, so visitors see a mix of old and new during the overlap, and a new server that is up but broken would take half the traffic. Needs: the option in `serve()`, then old SIGTERM only after the new one passes the health check. Failure handling: stop the new one; the old one never stopped. Entirely inside this repository.
- **Spare port, then swap**: start the new server on another port and health-check it. The swap still needs the main port freed and bound again, so a gap remains (shorter) unless something forwards traffic. It only helps with a forwarder, which is a new component or a proxy change.
- **Upgrader answers during the gap**: after stopping the old server, the upgrader binds the port itself and serves this page (with 503) until the new server is healthy, then closes it and starts the new one. A bind race between closing the placeholder and the new server binding remains, small but real; on failure the placeholder keeps serving until the old version is restarted by the existing recovery. Needs a small server module in this repository; no outside change. The gap becomes a donkey page rather than a browser error.
- **Proxy**: if the dashboard is reached through a proxy, the proxy shows its own error page while the upstream is down. Serving this page from the proxy (error page for 502/503/504) is a homeowner change in the private Infrastructure repository.

Recommendation: reusePort with health-checked handover removes the gap entirely, so build it first; the placeholder server is the fallback for the one upgrade that still has the gap and for crashes. Neither is built here.

## UI review evidence (issue #455)
A read-only page for browsing the evidence a UI/UX review leaves on Tower. `/evidence` lists review runs (newest first, with commit, data source, screenshot and before/after counts); `/evidence/<run>` shows the run's `manifest.json` facts, `report.md` (escaped text), before/after pairs side by side (stacked on a phone), and screenshots grouped as desktop, tablet and phone. It is linked from the System page (Dispatcher card), not from the navigation bar, and it is the same internal-only dashboard server: no new port, no new public exposure.

- **Where it reads:** only `<evidence root>/ui-review/<run>/`. The evidence root is `/mnt/cache/appdata/devtest-infrastructure/evidence` (D-005, D-006) unless `DASHBOARD_EVIDENCE_ROOT` names another. A run holds `report.md`, `manifest.json`, `*.png`, and at most one level of folders (`before/`, `after/`, or any other name) of `.png` files. No screenshot is committed to Git.
- **What it serves** (`/evidence/files/<run>/[<folder>/]<file>`): only `.png`, `.json` and `.md`, with a size cap per type; names are a closed character set, so `..`, slashes, backslashes, NUL, dot-files and double-encoded separators are refused (404). Every directory component is checked with `lstat` and the file is opened with `O_NOFOLLOW` and must be a regular file, so a symlink for a file, a folder, a run, or the `ui-review` folder itself is never followed and not listed.
- **Methods:** GET and HEAD only; everything else is the dashboard's existing 405. The Host check still applies. The evidence pages (and only they) allow images from the same origin in their content-security-policy; file responses carry `default-src 'none'; sandbox`.
- **Capturing the review pages:** `tests/dashboard-visual.mjs` stages every served dashboard file, derives its page list from the routes, and takes an optional page list as its third argument (for example `overview,work,evidence`); `DASH_EVIDENCE_ROOT` adds the evidence pages.
- **`GET /api/next`** (issue #518): returns only the app bar's Next element as an HTML fragment (`text/html`): `<b data-tick-state="scheduled|starting|overdue|running">…</b>`, or `<span class="muted">none</span>` when the server has no Next state. Same host and GET-only rules as `/api/view.json`. `dashui/app.js` fetches it when the countdown passes zero or a tick is running (at most once per 10 s), swaps the element in and re-localizes its times. When the answer is the `none` fallback it replaces the running or due element, so polling stops. Once the fallback is in place the status bar has no `[data-tick-state]` element, so the open page keeps showing `none` even if the server later reports a schedule, until the page reloads. It reloads itself every refresh interval (60 s by default, and the `<noscript>` meta refresh does the same without script), so no manual reload is needed. This is the same as a page first loaded in the `none` state, not a regression (issue #564). `tests/dashboard-next-tick.test.mjs` covers the scheduled, running, overdue and none answers and runs the real `localizeTimes` on a swapped-in element. Those tests use a fake DOM; on Tower, `ionice -c 3 nice -n 19 node tests/next-swap-smoke.mjs` (run `node browser/prepare-cache.mjs` once first; it needs the network and makes the git-ignored `browser/vendor/playwright-core-<version>.tgz`, and without it the smoke stops with a message saying so) runs the swap in real Chromium (pinned Playwright container, `browser/next-swap.mjs`): scheduled to `none` and scheduled to running, with the real DOMParser, selector, importNode and replaceWith (issue #564).

## Diagnostics tab (issue #496)
`/diagnostics` (read-only) shows where the cycle loses time, over the last 7 days (UTC days; the page states the window, and older history is not shown even though the supervisor keeps its own records longer). Sections: gaps between ticks (planned every 5 minutes, a gap of 10 minutes or more is a missed tick, lost minutes beyond the plan); job end to the next job start per agent (overlapping jobs are one busy span); review end to verdict recorded (carried verdicts are not counted); idle time by cause per day, which is `idleReport` from issue #487 called once per day, never recomputed; and load average, swap use and disk wait from the memory flight recorder `host-*.jsonl` samples (CPU time waiting on disk and blocked tasks stand in for disk I/O history).
Light by construction: tick, job and verdict figures come from files the dashboard already reads; the recorder folder is listed once and only `host-YYYYMMDD[-NNN].jsonl` files inside the window are opened (at most 40), each read at most 8 MiB and 48 MiB per page view, from the newest part when larger, and a file already read is extended only from where it stopped. No model call, no GitHub call. The folder is `/mnt/cache/logs/memory-flight-recorder`, or `DEVTEST_RECORDER_DIR` / the `recorderDir` handler option. A missing, empty or unreadable folder, an unreadable file or a damaged line is named on the page in fixed words (no path or log text is echoed) and the other sections still show. Figures are numbers only; no host name, address or secret is read or shown. Screenshots: `DASH_RECORDER_DIR=<folder> node tests/dashboard-visual.mjs <dir> diagnostics`.

Restart diagnostics and load tolerance (issue #632): after the new server first answers, it must stay running and answer three health probes in a row; a probe that fails while the process is still running is retried until 60 seconds have passed in total (a probe still pending then is cut off, so the wait never runs longer) (a dashboard view can take seconds to build under load), so a slow but healthy server is not rolled back. A process that has exited fails at once. A failed restart records a `cause` (`exited` or `unresponsive`) and `output`, the new process's own lines from `dashboard.log` written since it was started (redacted, at most 600 characters; a detached server's exit code cannot be observed), in `team/upgrades.jsonl` and in `dashboardFailure`. Retrying a commit whose pre-check was refused for an environmental reason is issue #581, not this change.

Issue #636 adds `GET /api/tests.json` (test-slot use and refused, timed-out, killed and orphaned runs, from `team/test-events.jsonl`) and `GET /api/ticks.json` (recent ticks and skipped ticks), read-only, for `foreman_tests` and `foreman_ticks`.

The same data is read through `foreman_diagnostics` (issue #635, `docs/foreman-mcp.md`) from `GET /api/diagnostics.json`.

## Foreman's self-check (issue #630)
Each tick, after planning, Foreman compares its own records with the pull request and issue lists that tick already read and with the running jobs (`supervisor/selfcheck.mjs`). It reads only: no model call, no extra GitHub request.
- **Fixed and logged** (the record is plainly stale and nothing can be lost): a recorded "Foreman added needs-homeowner" whose label is gone from a listed pull request or issue (and was recorded over 10 minutes ago). The record is dropped once and written to `selfcheck.log` in the state file; the tick report lists it under `selfChecked`.
  A target whose record also holds a fix-limit cause is never dropped, even when its label is removed and its other causes (for example `ci`) are stale: `Team.clearStale` owns that record and re-arms it only once a new head passes, so the stale `ci` record waits for it too.
- **Needs you, one item each while it lasts** (`selfcheck-job-<id>`, `selfcheck-review-<pr>`): a job recorded as running whose worker and provider process are gone (action: `ai-supervisor reconcile`), and a review that finished with no verdict, no refusal card, an open pull request at that head and no attempts left. An item keeps its first-seen time and disappears when the mismatch does, so it is not raised again each tick.
- **Already covered:** an issue marked implemented with no pull request is the existing `stale-mark-N` item (issue #521); the self-check counts it (`selfcheck.covered`) and raises nothing more.
When the records agree, nothing is changed or logged. Item text is redacted.

## A review result is never silently lost (issue #631)
- **Cheap repair.** When the validator refuses a review's verdict file, the one automatic retry is a short repair task (the job's `repairPrompt`: fix exactly the named error in the same file, no new review, no diff, no tests), not a repeat of the whole review. The refusal reason is shown as before (issue #550).
- **Findings are kept.** If the verdict still cannot be recorded, the Needs you card for the pull request lists the findings that could be read from the file (up to five shown, twenty kept in state), redacted and bounded, together with the file path. They are shown only; they are never posted or counted as a verdict.
- **Foreman's own faults are not charged.** The review attempt is handed back (once per head, reviewer and cause) when the job was lost to a checkpoint failure (`checkpoint-failure`), to a refusal the dispatcher could have predicted at ingestion, namely the reviewer model wrote the head or the exception step used the wrong model (`predictable-refusal`), or to an exception inside the verdict validator (`validator-fault`). The tick report lists them as `refundedAttempts`. A second failure of the same kind on the same head counts, so a loop still ends in Needs you.
